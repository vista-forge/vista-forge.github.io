Building Certo on vista-forge

Certo puts CPRS's chart review on a phone. To VistA it is CPRS. This page is how that was made true, and checked, and why it needed vista-forge to do it. Certo was named Loupe until 8 October 2026, and this page was first written under that name.

The Certo guide, for clinical staff · All artifacts

Abstract

Certo is a phone client for VistA that had to behave exactly as CPRS does: the same remote procedure calls (RPCs) with the same parameters, in CPRS's own context, the same order of checks, the same lists in the same order, and the same warnings in the same words. Most of that behaviour is written down nowhere but in two bodies of code, CPRS's Delphi source and VistA's M routines, and it shows only in the traffic between them. vista-forge made it measurable. An RPC tap recorded CPRS 1.33's own Broker traffic call by call. CPRS's Delphi source was read unit by unit. VistA's code and data were read live, on a YottaDB and an IRIS VistA, through one driver stack, and cross-checked against the vdocs corpus of VA documentation and the vista-meta model of VistA's code. Every write was first proven on a throwaway copy of the demo system, down to its database journal. Every behaviour became a test against a recorded reply. On 29 September 2026 the result was checked side by side with CPRS, screen for screen. In eight days, 22 to 29 September 2026, Certo matched or accounted for every one of CPRS's 75 sign-on, patient selection and alert capabilities, and 48 of its 63 reads are identical to CPRS's on the wire. Without the tap, the driver stack, the throwaway engines and the knowledge services, none of those claims could have been made, let alone tested.

1. Why a phone client had to be CPRS

A clinician who moves between CPRS on a workstation and Certo on a phone must find the same record, the same defaults and the same safeguards in both. VistA enforces its rules per client context, so Certo signs on in CPRS's own context, OR CPRS GUI CHART, and declares CPRS's build, 1.33.112.1. From then on VistA treats it as CPRS, and Certo has to act like CPRS in every call it makes: what it asks, in what order, with which parameters, and what it does with each reply.

The standard was set as "zero loss": every capability of CPRS's sign-on, patient selection and alerts either matched in Certo or ruled out by the operator, row by row, with the reason written down. Nothing dropped by omission. Matching means the same RPCs with the same parameters, the same defaults read from VistA, the same lists in the same order, and the same warnings and refusals in the same words.

None of that can be taken from memory or from documentation alone. CPRS sorts its lists itself, with Windows' word sort. It sends a person's saved alert sort back to VistA every time its selection window opens. Its patient selection runs its checks in one fixed order: the same-SSN check, the record check, the date of death, then the selection. The only record of these is CPRS's source, and the only proof is its traffic.

2. The method, in seven steps

  1. Read CPRS's own code

    Each screen was built by reading the CPRS 1.33.112.1 Delphi unit that draws it, the build the reference workstation runs, and following it: its order of checks, its lists' sort orders, its lookup patterns and its words. Certo's code and tests cite 40 CPRS source files by name. The ones behind sign-on and selection:

    • Loginfrm.pas · SelDiv.passign-on and the division choice
    • fPtSel.paspatient selection, its OK's checks in order, and alerts: Process, Remove, Defer
    • mPtSelOptns.pas · rCore.pasCPRS's lists, their sort orders, SSN lookups, Save Settings
    • mPtSelDemog.pasthe Details preview
    • fDupPts.pas · uSimilarNames.passimilar patients and similar provider names
    • fFrame.pasopening a patient: the flag window, lookup messages, the version check
    • fTimeout.pasthe CPRS Timeout window, its count and its timing
    • fMeds.pas · rMeds.pas · fProbs.pasthe Meds and Problems tabs
    • fNotes.pasSearch for Text in the notes
    • fDeferDialog.pas · fAlertsProcessed.pasDefer, and the Processed alerts

  2. Read VistA's side, live

    What CPRS asks for is answered by M routines. Their source, the FileMan files they read and the parameters they consult were read on the running systems through vista-forge's driver stack (m engine exec), read-only, never by hand-rolled access to the engine. Certo's code names 174 entry points in 97 VistA routines, each where its behaviour is followed. Counts that shaped decisions were measured this way rather than assumed: for example, 479 patients with an alias, 11 PCMM teams, one deceased patient on the demo system.

    Two knowledge services cross-checked what was read. vdocs is a gold corpus of VA's VistA documentation, searched and cited by section. vista-meta is a measured model of VistA's code and data: which routine an RPC runs, who calls what, and how many records a file holds. Both are served to Claude as MCP tools. What the documents say and what the system measurably is were kept apart and labelled.

  3. Record CPRS itself with the RPC tap

    vista-forge's RPC tap (v rpc-tap) splices VistA's Broker parser, copies each call and reply into a bounded ring per job, and drains it read-only. It was installed as a KIDS build with v pkg and removed again, verified clean, with the original routine restored exactly. CPRS 1.33 ran in a Windows VM against the demo system through v rpc relay. The operator signed on, Claude drove the VM from screenshots, and each screen was checked against the tap's recording. The tap's converter drops every sign-on call that carries a code or a one-time Kernel token, so no credential ever reaches a recording.

    Five recording sittings between 23 and 28 September 2026 left 10 recordings, kept in Certo's repository as tests: 691 CPRS calls across 141 distinct RPCs.

  4. Speak CPRS's protocol

    Certo reaches VistA only as CPRS does: through the RPC Broker, signed on as the person, through v-base's Broker client. It asks for the introductory text before any code, as CPRS's form does. It signs on in CPRS's context and declares CPRS's build. The person's codes are used once and kept nowhere: not in the session, not in a log, not in an error. VistA's own answers come back in VistA's own words.

  5. Hold every call to CPRS in a test

    Each of Certo's reads carries a verdict against CPRS's recorded call for the same screen. Same means the same RPC, the same parameters on the wire and the same reply. Same reply means CPRS reached the same data by another route. Ruled means one parameter differs by the operator's decision. No screen means no recorded CPRS screen shows it. Any read without a verdict fails the build.

    A coverage table lists CPRS's sign-on, patient selection and alert capabilities from its source, one row each. The build gate fails on a row with no status, on a built row whose test is missing, and on any selection RPC Certo calls that no row names. Each kind of failure was proven by planting it. Every live finding became a test against a recorded reply, 174 of them, and a live twin, run only by make check-live, confirms the recording is still what the demo system answers.

  6. Prove every write on a throwaway copy

    Some of CPRS's actions write: the audit bulletin after a restricted record is confirmed, a deferred alert, a removed one. None of these was proven first on the gold system. A throwaway copy of the demo system was made from its nightly backup, on a network with no way out, and removed after, with its removal measured. The states the demo system cannot hold were made on the copy with VistA's own filers: a locked device, a verify code that must change, a second division, a restricted list, alerts to act on.

    For the confirm of a restricted record, Certo's run was held against CPRS's own run on the copy. A written equivalence, committed before either run, compared them call by call (seven traffic rules) and write by write in the YottaDB journal (four database rules). No finding: the same security-log entry, the same bulletin, in CPRS's order.

  7. Check it side by side

    Last, CPRS and Certo were run at the same time on the demo system, as two people whose settings differ, and walked capability by capability: the same screen, the same lists in the same order, the same windows in the same words. The measurements are below.

4. Checked side by side

CPRS 1.33 and Certo were run side by side on VA's demo VistA, signed on at the same time as two people whose settings differ, VEHU,TEN and PROVIDER,FORTY. Each capability of sign-on, patient selection and alerts was walked on both: the same screen in each, the same lists in the same order, the same defaults read from VistA, the same warnings and refusals in the same words. The check found three defects in Certo, each fixed and seen fixed on the phone before it closed, and two CPRS buttons the capability list had missed, now added to it.

5. Two live VistA systems, and copies of one

  • vehu, VA's demo VistA on YottaDB, with its RPC Broker, Kernel, FileMan and test people. Every recording, live read and live test ran here, as a person signed on, with every write named and sanctioned first. Its nightly backup is the source of the throwaway copies.
  • foia-iris, VistA on InterSystems IRIS, reached through the same driver stack. It was measured alongside vehu where the two differ, for example whether a person may hold two sessions at once, which decides whether Certo can run beside an open CPRS.
  • Throwaway copies of vehu, made three times for Certo between 26 and 29 September 2026, from the nightly backup, on an isolated network at a fixed address, run for one session and then removed, with the removal measured. Each state and write was made and proven there, never on the gold system.

The same M is read on both engines through one seam, the driver SDK, so a measurement means the same thing on either, and no tool reaches an engine any other way.
