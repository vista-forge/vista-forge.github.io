Abstract

CPRS is three things in one program: a presenter of VistA's data, an interpreter of each site's clinical definitions, and an orchestrator of multi-step clinical transactions. Measured today, its compiled Delphi code is 355,291 lines in 519 units, holding 14,014 routines, of which 4,061 are event handlers. It reaches VistA through 1,190 remote procedures in its context. Those enter VistA through 232 routines whose call graph reaches up to 7,290 routines and about 998,000 lines of M in 76 packages. It renders tens of thousands of site-defined records: 10,099 reminder-dialog elements, 5,836 note templates and 759 order-dialog entries on vehu. It also leans on the Windows desktop for PIV signing, CCOW, COM extensions, local programs, printers and screen readers.

This plan keeps VistA's clinical rules where they are and calls them. It moves the client's interpreters and orchestration into server-side domain services, and it presents them in two web front-ends. Classic mode reproduces CPRS's screens. Modern mode follows the Office-on-the-web look and runs beside Teams and Outlook in Edge. Underneath the services, a CPRS-equivalence layer holds each person's Broker session and sends what CPRS would send. It enforces the duties VistA leaves to the client: the audited sensitive-record check, signature validation before orders are signed, lock release and keep-alive. Identity is OpenID Connect at the front, with access/verify as the baseline. VA's SSOi token path and a proposed JWT verifier inside VistA connect the two. Third-party and AI clients use the same services with scoped, on-behalf-of tokens. They never sign.

Fidelity is measured, not asserted. Every Delphi routine, every RPC, every user action, every site-definition record, every duty and every outside dependency gets a disposition from a closed list. A disposition counts only when its proof passes on the commit: a ported test, a recorded-traffic conformance scenario, a database diff or a screenshot diff. The headline number is the share of each population that is proven. "100%" means no item is left unknown and every proof is green. It does not mean every line was executed. The plan builds on two parked proposals from 2026-09-23, the CPRS surface map and the CPRS service layer. Both meet their stated conditions for unparking with this request. It corrects several of their snapshot numbers using later measurements, which are listed in §20.

1The request and where it lands

The request is a drop-in web replacement for CPRS that keeps all of its behaviour. It should be built as services rather than RPC wrappers, measured by coverage of CPRS's Delphi code and of the RPCs CPRS uses, and offered in a classic mode now and a modern mode later. Web, mobile and third-party clients, including AI-driven order entry, consume the same services.

This is not the first time the question has been asked here. Five earlier efforts bear on it:

  • CPRS surface map (parked 2026-09-23). It proposed fourteen generated artifacts (an action map, screen specifications, reply schemas, a client-logic inventory, site-definition interpreters, workflows, an authorization matrix, external integrations, a data map, a server-effect register, a conformance suite, a readiness register, a client-obligations register and a facet registry). It was parked because nothing consumed it. Its condition for unparking is "a consumer is named for a whole-surface artifact … or a web-UI effort". This request names that consumer.
  • CPRS service layer (parked 2026-09-23, five safeguards ruled). One server holds each person's Broker session and offers clinician-shaped services. Its condition for unparking is "an effort commits to a client that must reach VistA through one server holding people's sessions (a web CPRS …)". This request meets it. Its adversarial review recommends ruling a session guard first and coarse services after; §9 follows that.
  • Loupe (accepted, building). A phone client for clinicians that reaches VistA as the signed-on person through CPRS's own RPCs. It has a passed side-by-side exit test for sign-on and patient selection (2026-09-29). It is the nearest working precedent for a client held to CPRS's behaviour, but it is a phone summary with ruled differences from CPRS, and it should become a client of the services.
  • The retired web-CPRS architecture (June 2026, retired for having no consumer). It dispatched calls through a new component inside VistA and used pooled workers. The service layer's rulings reject both.
  • An exploratory cprs-web project outside the org (~/careflows/cprs-web, May to July 2026). It planned an AWS deployment across about 130 VistA instances with a per-site behaviour profile, named six client engines and captured a golden traffic corpus. It is useful as reading. Under the org's boundary rule, nothing here may depend on it.

The org's settled position on whole-record extracts also applies. VPR and eHMP extracts are not a new client's foundation (ruled 2026-09-23). The client uses CPRS's RPCs.

  1. VistA's clinical rules must be called, not rewritten. CPRS asks the server for dose conversions, days supply, order checks, cosignature and release rules. The M behind CPRS's RPCs reaches about a quarter of VistA's 4.1 million lines. A web CPRS that re-implements any of that is a new EHR, not a replacement.
  2. The client's real weight is in its interpreters. The order-dialog, encounter, note-template, reminder-dialog and consult engines alone hold about 126,000 lines. Each turns site data into screens and into the exact strings VistA expects back. These are the "engines" to isolate (§4).
  3. VistA trusts the client for duties it does not enforce. The sensitive-record check is itself the audited access. ORWDX SEND never reads the signature code it is given. ORWD SIGN signs orders on the ORES key alone and CPRS never calls it. The Restricted Patient List exists only in which lookup the client chooses. A service layer must carry each of these as a rule, with a test that fails a service that skips it (§6).
  4. "Call for call" needs a written equivalence. CPRS's patient-selection preamble is deterministic (36 calls, identical across three sessions). After it, traffic depends on the showing tab, the cache and timers. Conformance compares functional calls under a stated CPRS state, with timers and polls removed and record numbers normalized (ruled 2026-09-23).
  5. Half the outside surface is on the server. All 18 of vehu's outbound web servers point at hosts it cannot reach, so order checks, PDMP, DST and primary-care detail run in outage mode on vehu and on any copy of it. A recording there captures outage behaviour.
  6. A full Delphi line-coverage run looks feasible but is unproven. All 419 units the project file lists are present. Only UJawsLauncher and the open-source FastMM4 are missing from the tree. The other outside units it compiles against (Indy, the Office automation units, TeeChart) normally ship with Delphi, though which edition is needed is unverified. The release build carries no debug map, so instrumented coverage needs a rebuild in a Windows guest with the matching Delphi compiler. That rebuild has not been attempted (§17).
  7. Every major vendor that made this move kept a native shell. Epic's Hyperdrive is an installed Chromium-based client with local helper software for signature pads. The new Outlook and the new Teams run as web apps inside Edge WebView2. The plan is browser-first, with an optional desktop companion for the integrations a browser cannot reach (§13).

Two points follow from the table.

  • The interpreters carry the clinical text. The template engine assembles the note that a clinician signs, and the reminder engine writes encounter data, orders and note text together. A port is acceptable only when, given the same definitions and the same answers, it produces byte-identical text and identical filing calls (§11, oracle 3).
  • The "RPC names" column undercounts real reach. The forms call wrappers in the core units, so most names sit in a handful of units such as rCore and rOrders. The action map, which traces each user action to the RPCs it reaches, is what assigns RPCs to engines (surface map A1).

RPC names arrive at run time through six channels: report definitions, the cover-sheet list, the Labs tab, graphs, remote sites (XWB REMOTE RPC, XWB DIRECT RPC) and COM extensions, which can call any RPC in any context the person holds. A static census alone is therefore never complete. The census is taken by call form, never by intersecting strings with the RPC file, and every name the server lacks is reported rather than filtered out.

CPRS is not one context or one connection. It switches to EC GUI CONTEXT (61 RPCs) for Event Capture. It gives COM extensions SetContext and CallRPC. It opens further Broker connections by one-time token for the debug report, the Vitals DLL and the Event Capture program it launches. Its Broker copy also carries an SSH-tunnel mode (plink) measured.

Every RPC gets a disposition (§11): delegated to VistA through a named service action, retired, forbidden, or UI state that the new client keeps in its own preferences store. ORWD SIGN is in the context, signs orders with no signature code and is never called by CPRS. It must be forbidden by the equivalence layer's allowlist.

The Tools menu on vehu

The menu is the parameter ORWT TOOLS MENU, set at user, location, service, division or system level. Each entry is NAME=COMMAND, and "the COMMAND may be a line that can be executed by Windows" documented. CPRS substitutes %SRV, %PORT, %DFN, %DUZ and %MREF before launching. vehu holds nine entries measured:

  • local programs with a VistA hand-off: VistA Imaging Display and Capture (%DFN %MREF %SRV %PORT), Mental Health Assistant (s=%SRV p=%PORT c=%DFN u=%DUZ m=%MREF);
  • web pages: VistaWeb (an intranet URL, user level), Veteran Health Library, two Primary Care Almanac links (one substitutes %DUZ), eHMP and an HMP sandbox.

Web pages map cleanly to links. The local programs need the companion and a hand-off that does not depend on the CPRS process's Broker connection. %MREF carries a reference for the launched program to reach VistA as the same person. Its web successor is a one-time VistA token minted by the equivalence layer (§10).

Server-side outside connections

Order checks (drug interactions through the PEPS server), PDMP, consult decision support, primary-care detail and the audit service call 18 outbound web servers. All 18 on vehu point at hosts it cannot reach; one "PDMP TEST SERVER" is www.yahoo.com measured 2026-09-23. These do not move. The web client inherits them unchanged because it calls the same RPCs, but every scenario recorded on vehu that touches them records outage behaviour and must say so.

8How others moved thick clients to the web

Epic: Hyperspace to Hyperdrive external

Hyperdrive is "a specialized web-browser, like Google Chrome or Microsoft Edge, but used exclusively to access a web-based version of Epic", Chromium-based, rolled out from 2022 with migrations continuing through 2024–25. It is installed, not a bare browser tab. Signature pads work through vendor software "installed on the local computer system". Badge-tap sign-in and controlled-substance signing come through Imprivata. Implementers report that COM integrations written for Hyperspace "often need to be updated". Lesson: a clinical web client still needs a native foothold for devices, strong authentication and legacy integrations. That foothold should be small and specific.

Microsoft Teams: Electron and AngularJS to WebView2 and React external

The new Teams (general availability 31 October 2023) dropped Electron for Edge WebView2 and moved from AngularJS to React with the Fluent design language. Microsoft reported up to 2× faster and up to 50% less memory. Lesson: one web code base inside a thin native host is the current pattern, and the host can be swapped without rewriting the app.

Microsoft Outlook: "One Outlook" external

The new Outlook for Windows is Outlook on the web inside WebView2, one code base and one interface across PC, Mac and web. Microsoft ran it beside classic Outlook for years as an opt-in preview. Lesson: parallel run with per-user opt-in, and the old client stays available until parity is proven. Modern mode should look like this family so it sits beside Teams and Outlook tabs in Edge.

Microsoft Office on the web external

Office Web Apps appeared in 2008–09. Microsoft describes cross-platform Office as a shared core of C++ code behind platform abstraction layers, with no platform conditionals in the shared code. Excel Calculation Services ran workbook calculation on a server. Lesson: isolate the engines from the presentation and run them in one place. That is the move from Delphi interpreters to server-side engines here.

MEDITECH: MAGIC and Client/Server to Expanse external

Expanse, a web-based EHR, launched in February 2018. Migrating customers found that only a subset of legacy data moves, so the old platform or an archive remains. Lesson: here there is no data migration at all. The web client reads and writes the same VistA, which removes the largest risk such migrations carry.

Oracle Health: a rebuilt EHR external

Oracle announced in October 2024 a next-generation EHR built from the ground up on its cloud, ambulatory first, with acute care planned for 2026. It was not built on the existing Millennium client. Lesson: a ground-up rebuild trades fidelity for freedom. This plan takes the opposite trade on purpose.

VA's own attempts

VA contracted eHMP in 2014 ($162 million to Accenture Federal Services) as CPRS's successor external. VA's own Tools menu on vehu still lists eHMP measured. eHMP installed its own package inside VistA (43 HMP RPCs, 128 routines) and called 45 RPCs directly from its resource code measured 2026-09-23. VA's "Cloud CPRS" streams the existing Delphi client behind Okta multi-factor sign-in for about 32,000 staff a month (VA privacy impact assessment, 2025). Lesson: a successor that changed VistA and the workflows at once did not replace CPRS. Streaming the old client is VA's current answer to remote access, and it is not a web client.

Patterns this plan uses. It strangles the old client screen by screen, with both clients live on the same VistA. It runs the two in parallel per person. It pins behaviour with characterization tests taken from the running legacy system (golden masters). It puts an anti-corruption layer between modern services and the RPC protocol, and a per-client backend that holds tokens on the server (the backend-for-frontend pattern the IETF's browser-app guidance recommends).

9Target architecture

Two tiers, so coarse services can still be held to CPRS

The service layer's review found that coarse services and call-for-call emulation pull apart. A cover-sheet service that composes thirteen RPCs is not any single CPRS action. This plan separates the two:

  • The equivalence layer offers only CPRS-shaped actions. Each action is one thing CPRS does, such as opening a chart, loading an order dialog, accepting order checks or signing a note. It is held to CPRS's recorded traffic under the written equivalence. Its allowlist comes from the surface map's census. It applies the duty rules.
  • Domain services compose those actions into workflow-shaped APIs. A composition with no CPRS counterpart, such as a team's overnight summary, is held to its own contract tests and labelled that way. A service can never send an RPC except through an action. "Not piecemeal wrapping" is therefore a property of the API, while fidelity is a property of the layer beneath it.

Service boundaries

The boundaries come from measurement. 941 of the 995 context RPCs that CPRS's code names are called from exactly one area of the client, and 54 are shared (note text, signing, copy/paste, title lists, remote calls) measured 2026-09-23. The shared 54 form the platform services, built first. Each domain service owns one clinical aggregate (a patient's chart context, an order, a document, an encounter, a consult, an alert) and publishes events when it changes. Clients do not poll VistA. A notification or a background job's result is pushed to them.

Where it runs

CPRS's traffic is chatty: 36 calls to select a patient and about 45 for a cover sheet. Each person's session is a VistA process. So the services run as a cell next to each VistA instance, on the same network segment, and the browser reaches the cell over HTTPS. "Cloud" means the cells and the identity front door run in VA's cloud next to cloud-hosted VistA. They never sit across a wide-area link from the Broker. One cell serves one VistA instance. A site registry maps a station to its cell and to the CPRS version it emulates.

What "100%" means. No item in any population is unknown, and every disposition's proof is green on the commit. It does not mean every Delphi line ran. Error paths, defensive branches and dead features make full execution unattainable, and chasing it would reward tests that exercise nothing clinical. "CPRS exercised" exists to show where the scenario corpus is thin, not to certify replacement.

The five oracles behind the proofs.

  1. Traffic: the tap records CPRS and the equivalence layer doing the same action. Functional calls are compared under a stated CPRS state, with timers, polls and UI-state calls removed and record numbers and times normalized ruled.
  2. Database effect: writes run on a throwaway copy of vehu, never gold, and a before-and-after diff of the affected globals must match. The tap sees traffic, not writes.
  3. Text: engines that produce clinical text (templates, reminder dialogs, order text) must produce byte-identical output for the same definitions and answers.
  4. Screen: classic mode is compared with CPRS by screenshot, after the CPRS source has been read for sorting and casing rules. CPRS re-cases VistA's words and re-sorts lists, so the reference is CPRS's screen, not VistA's reply.
  5. Refusal: each duty's negative scenario must fail a service that skips the duty.

Baseline on 2026-10-03. Nothing is ported, so code replaced and RPCs replaced are 0%. The first dispositions that can be proven now are static. The closure analysis already marks 49 units (23,845 lines, 726 routines) dead or tooling-only, including the old fCover.pas and the unreferenced COM-server unit uComServ.pas. These sit outside P1.

Instrumented coverage of CPRS itself. The release build has no debug information. An open-source Delphi coverage tool (DelphiCodeCoverage) needs a detailed map file from a rebuild external. The tree looks buildable (§2, finding 6). The project file's version stamp, 20.1, suggests RAD Studio 12 (inferred, not verified). The rebuild would run in the Windows guest that already hosts CPRS on this box. If it fails, a fallback is binary instrumentation mapped to the method names Delphi's run-time type information exposes, which covers published methods such as event handlers.

12Classic and modern modes

Classic mode: CPRS's screens, generated from its forms

CPRS's 312 forms are stored as text measured. They hold 7,559 components of 414 classes, 4,431 event bindings, 1,096 menu items, 184 actions, 47 tab sheets, 25 timers and 253 accessibility managers. The most common controls are panels (994), labels (702), buttons (683), long-list combo boxes (256) and list boxes (136). 100 controls page data from the server on demand. Classic mode is generated from this material and not drawn by hand:

  • a form reader produces a screen description for each form (geometry, captions, tab order, menus, shortcuts and accessibility names), and a web renderer draws it at CPRS's layout;
  • each CPRS control class maps to one web component with the same keyboard behaviour, such as the long-list combo box with incremental server paging and FileMan-style date entry;
  • the CPRS-specific behaviours read from source are carried exactly: list sorting by Windows' word order or by ASCII depending on the list, re-casing of VistA's text, placement of medications by order-id letter;
  • dialogs, confirmations and their wording come from the source strings;
  • each screen passes a screenshot comparison against CPRS in the Windows guest before it counts.

Modern mode: the Office-on-the-web family

Modern mode uses the same services, the same workflows and the same duties. Only the presentation changes: Fluent-style components, a left rail, a command bar, panes and cards, light and dark themes. It is installable as a web app in Edge, so a clinician can keep Outlook, Teams and the chart open as tabs or windows, as the request describes. A Teams tab is a later option, because a Teams tab is a web page. Since every rule lives in the services, the two modes cannot diverge in what they allow. One person can switch modes mid-session without losing state.

14Third-party and AI clients

The domain services are the API. Third parties use them as web and mobile do, with four limits:

  • Always on behalf of a signed-in person. A third-party or AI client holds a scoped token that the identity service issued for one person. Each call runs in that person's Broker session. There is no service identity, which follows the ruling that every call goes out as the person.
  • Scopes follow the services: read a chart, draft a note, draft orders, process alerts. A scope never exceeds what the person may do in VistA.
  • Agents draft; people sign. AI-driven order entry produces unsigned orders through the same order-dialog engine, so quick orders, order checks and the site's dialogs all apply. The order checks reach a person before anything is saved. Signing requires the person's signature code or PIV card in a CPRS-shaped signing flow. No scope can sign.
  • Values come from VistA through code. A model never retypes a value it was shown, and it never assembles a raw RPC. The same rules govern Loupe's agent today.

A FHIR facade over the read services is a later option for interoperability. It is not the internal model, because it loses CPRS's site-specific detail.

18Assumptions

  • The target is CPRS 1.33.112.1 with OR*3.0*629, the build in the Windows guest and the source on this box. A later CPRS build is a regeneration, not a redesign.
  • VistA is not changed, except for a later ruled exception (the JWT verifier) installed as a KIDS build through v pkg.
  • CPRS remains installed and usable throughout. Both clients run against the same VistA, and multiple sign-on is decided by Kernel's per-person setting.
  • Every call runs as the signed-on person in that person's own Broker session.
  • A throwaway copy of the vehu image is a full VistA and is the only place writes are recorded.
  • vehu and its tap recordings are representative of a VA site's CPRS behaviour apart from outside services, data volume and local configuration.
  • The web client must meet Section 508 (WCAG 2.0 AA as the 508 refresh incorporates it).
  • Edge is the managed browser, so WebView2 is available for a companion.
  • Service cells can be placed next to each VistA instance on the same network.
  • Signing stays a human act. No automated client signs anything.
  • The effort lives in the org as a VistA-layer effort and reaches VistA only as a Broker client through v-base's broker package. A new Broker door of this kind needs its own ruling with a retirement condition.
