Abstract

CPRS is three things in one program: a presenter of VistA's data, an interpreter of each site's clinical definitions, and an orchestrator of multi-step clinical transactions. Measured today, its compiled Delphi code is 355,291 lines in 519 units with 13,625 routine bodies, and the Vitals entry DLL it loads adds 28,911 lines and 1,195 more. CPRS and that DLL name 1,067 remote procedures: 1,055 that vehu has and 12 it lacks. CPRS's context admits 1,190, so 166 are admitted and never used. Behind those RPCs a label-level scan reaches at least 156,509 lines of M in 2,637 routines. Five groups of CPRS units build screens from site definitions at run time by two independent signals (order dialogs, note templates, reminder dialogs, immunizations and pathology orders, about 94,000 lines), and the Vitals DLL passes the same test. Two more groups pass one signal, and nine let site definitions decide what fixed screens show.

The plan keeps VistA's clinical rules where they are and calls them. Rewriting them outside VistA, the route of the operator's 2016–2019 projects, was measured twice. It is declined for the calls that write, and held as an option for the calls that write nothing stored (§8). It moves the client's interpreters and orchestration into one session service per VistA, organised as domain modules behind a workflow-shaped API, and presents that API in two web front-ends: a classic mode that reproduces CPRS's screens and a modern mode in the Office-on-the-web family. The session service holds each person's own VistA session, sends only the calls CPRS uses, and applies the duties VistA leaves to the client. Every call leaves it through one typed RPC call described by a registry. Its rules apply at that call, and a back end could later change there one call at a time (§9). Four of those duties were run live on a throwaway copy of VistA on 2026-10-03. VistA signed an order, and released a discontinue, on a signature code it had just declared invalid. It let a user whose write access is "no" create a note and sign an order. It served a patient outside a user's restricted list. It freed a dropped client's locks within three seconds. So the service validates the signature code before any order is sent, applies the write-access rules, binds every patient-scoped call to the patient the session selected and checked, and ends a departed client's session. Those guarantees cover traffic through the service; with no change to VistA, the Broker stays open to CPRS itself. A second door on the same session core, speaking the Broker's own protocol, is proposed to bring unchanged CPRS under the same rules, observing first and refusing later. Identity is OpenID Connect at the front, with access and verify codes as the baseline and VA's token path as the route that works at VA today. At VA the plan signs people in through VA's own identity services as they stand. Kernel sees only a level of assurance and treats every level from 2 up alike. So a simpler sign-in than the PIV card can be added at the identity provider with no change to VistA, and holding sign-in to the ruled floor is the service's duty (§10). AI and third-party clients draft proposals that a person accepts. Where Kernel allows the person a second sign-on they read through a VistA job of their own; where it does not, they make no VistA calls. They never sign.

Fidelity is proven by capability rows, the unit Loupe already uses: one CPRS behaviour per row, read from the source, each one built with tests as evidence or closed by a ruling. The routine and RPC counts are completeness checks on the rows. They are not the proof. A row census projected from Loupe's one data point puts the whole client at roughly 1,300 to 4,400 rows, and about 3,200 by a second basis. Two tracks are kept apart: a reference implementation proven against CPRS on demo VistA, which this org can build and test, and deployment at VA, which depends on approvals, licensing and data volumes that nothing here can measure. This version carries the thirteen changes of the first adversarial review, the ten of the second, the six of the third, five of the fourth and the ten of the fifth (§21). After a serial spine of three phases the work fans out into lanes, and the measured dependencies let about six run side by side (§15). What clinicians actually do is known here only from recordings made by hand on demo data. An analysis of production traffic at two VA medical centers exists and is not yet on this box. The plan takes it as an enabler for its three hardest workflows, order entry, notes and reminder dialogs. It supplies the flows and parameter classes to build from, the order of the work and a scenario list drawn from real use. The proof stays with tests made here (§11, §15). Every proof in this plan compares the new client with CPRS, and CPRS has so far been recorded sending 237 of the 1,067 RPCs: 38 of the 369 in the orders lane. So the plan's first product is a reference factory, which drives, records and compares CPRS on throwaway copies with nobody at the keyboard. With it a row's evidence is checked by machine, and the operator's time goes to rulings (§23).

1The request, and the two tracks

The request is a drop-in web replacement for CPRS that keeps all of its behaviour. It should be built as services, measured by coverage of CPRS's Delphi code and of the RPCs CPRS uses, and offered in a classic mode now and a modern mode later. Web, mobile and third-party clients, including AI-driven order entry, use the same services.

  1. VistA's clinical rules must be called, not rewritten. CPRS asks the server for dose conversions, days supply, order checks, cosignature and release rules. The order-check, save and send calls each reach about 55,000 to 60,000 lines of M.
  2. VistA does not check an order's signature code, and does not apply the write-access rules. Both were run live. A made-up code signed an order and released a discontinue. A user with write access "no" created a note and signed an order. A note signature with the same code was refused (§6).
  3. VistA serves any patient to any signed-on user. A user restricted to a two-patient list was given an outside patient's name, date of birth and SSN. The session service must bind every patient-scoped call to the patient it selected and checked: 217 of the RPCs CPRS uses take a patient parameter, and 107 of those write (§6).
  4. The client's weight is in what it builds from site data. Five groups in CPRS and the Vitals DLL are interpreters by two signals, two groups by one, and nine are steered by definitions (§4).
  5. The back end is one stateful service per VistA. A person's Broker connection answers one request at a time and workflow state lives in the VistA job behind it. A dropped connection's locks were free three seconds later, so rebuilding unfinished work after a restart is a replay with failure cases. Sessions of different people are independent, so a cell scales and is released by session and never by module (§9).
  6. Fidelity is proven by capability rows. Single Delphi routines run past 1,100 lines, and 89% of RPCs are called from one place and vary only in their parameters. Counting routines or RPC names can reach 100% on a wrong product (§11).
  7. CPRS's own keys need more than a browser tab. 29 of CPRS's 244 shortcuts use keys a tab will not release. The routes are the desktop companion, or full screen with the browser's Keyboard Lock (§12).
  8. An agent cannot always have its own VistA job. A second sign-on was refused for a person whose multiple sign-on is "not allowed", and an agent inside the clinician's job would clear the clinician's order checks (§14).
  9. Half the outside surface is on the server, and vehu cannot show it. All 18 outbound web servers on vehu point at unreachable hosts, and vehu has no usable printer.
  10. VA already runs a service adapter over these RPCs. Its context on vehu admits 262 RPCs, 178 of them CPRS's, including order send and note sign, and it added 47 RPCs of its own inside VistA (§8).
  11. A rebuild of CPRS with coverage instrumentation is unproven. All 419 units the project lists are present and the forms have no hidden third-party components, but the build notes in the source mirror are for a much older CPRS (§17).
  12. Emulating VistA's side was tried, and it reached the shallow end. Across its two designs the operator's 2016–2019 archive holds 198 RPC models, 186 of them among the RPCs CPRS uses. By this plan's scan 34 of those can write stored data. An encounter save was emulated in the 2017 design; nothing covers orders, note signature, order checks or consults. Together they reach a fifth of the M behind CPRS's used RPCs (§8).
  13. The work cuts at the RPCs, and CPRS's own units are no guide. Twenty-one of CPRS's 28 feature groups sit in one dependency cycle, while 953 of 999 RPCs belong to one group each. Built actions first, the work falls into 41 tracks in four waves, and up to six lanes can run side by side at almost no cost in waiting (§15).
  14. The M behind CPRS's RPCs divides in two. The 720 used RPCs that write no stored data reach 19% of it. The 335 that write reach 91%, about four fifths of that outside Order Entry. Emulation is declined for the second group and held as an option for the first (§8).
  15. An analysis of real use can carry the hardest part. This plan's recordings reach 237 of the 1,067 RPCs, clicked by hand on demo data. VA's VistA Application Analytics analysed production traffic from two medical centers, mostly for order entry, note creation and reminder dialogs operator's account. It has not been read here. Once it is, it gives the flows and the parameter classes to build from in the three workflows where this plan is weakest (§8, §15).
  16. Kernel does not see how a person signed in. Its token sign-on reads who the person is and a level of assurance. It refuses a level below 2 and treats every level from 2 up alike, a directory password included. So a sign-in simpler than the PIV card, by the computer's own unlock, a security key or the person's phone, needs no VistA change. Refusing a weak sign-in is left to the client (§6, §10).
  17. The reference recordings are the critical path. CPRS has been recorded sending 237 of the 1,067 RPCs: 38 of the 369 the orders lane names, and 71 of the 319 that write. A test cannot be written first where its reference does not exist, and a recording today needs the operator at every session (§23).
  18. Six lanes do not multiply the operator or the reference CPRS. Loupe's 75 rows took 61 numbered rulings and a side-by-side test by eye, and there is one Windows guest. A row's proof has to be checked by machine, so that the operator rules differences and does not review rows (§23).

4The engines inside the Delphi client

Every compiled unit was assigned to one group by folder and file name. Each group is then classified by a stated test on measured signals. Version 2 used one control signal and found six interpreters; a second review round showed three of them sat exactly on the threshold and a second signal disagreed on two. This version uses both signals.

The test. For each group, from compiled code:

  • controls constructed at run time: constructor calls on visual control classes;
  • controls parented at run time: assignments of a parent to a control;
  • reply parsing: Piece() calls per 1,000 lines;
  • definition files read: for every RPC the group names, the server code was scanned label by label, three calls deep, within and between routines, for eighteen site-definition files. The number after each file is how many of the group's RPCs reach it.

A group is an interpreter when its RPCs read a definition file and both control signals reach 10. It is an interpreter on one signal when only one does. It is definition-driven when neither does and either five or more of its RPCs read one definition file, or it parses replies at 40 or more per 1,000 lines and reads a definition file. Everything else is fixed. The thresholds are a choice. The columns are there so a reader can move them.

What the test shows:

  • Five interpreters, about 94,000 lines: order dialogs, note templates, reminder dialogs, the pathology order builder and immunizations. The shared dialog components (804 lines, no RPCs) are the layer both the template and reminder engines draw with and count with them.
  • How firm that is. The template and immunization engines are interpreters under every variant tried: either signal, thresholds of 5, 10 and 15, and scan depths of one call to unlimited. Order dialogs, reminder dialogs and the pathology builder have exactly 10 constructor sites and are carried by the second signal (32, 11 and 17). Reminder dialogs pass both narrowly.
  • Two groups pass one signal. The cover sheet constructs 32 controls and parents 5. The application shell constructs 1 and parents 12. Both read definition files, and both are built as engines in §9 whatever the label.
  • The Labs tab is the report engine again. Its largest handler has the same name and job as the Reports tab's (1,258 and 1,101 lines, 206 identical lines), and the two tabs and graphing parse replies at 48 to 58 per 1,000 lines, the highest in the client.
  • Encounter, consults, notes and order management are steered by definitions and build few controls. Their screens are fixed and the definitions fill them.
  • Notifications are fixed. Follow-up is a case over 50 constants in the main frame.
  • The Vitals DLL passes the test too: 15 controls constructed, 10 parented, and 8 of its 33 RPCs read the vitals type and qualifier files.
  • The write-access unit is a permission engine, treated in §6.

An acceptable port of an interpreter produces, for the same definitions and the same answers, byte-identical clinical text and identical filing calls (§11).

9Target architecture

Service-shaped at the API, one session holder behind it

The request asks for services and not piecemeal RPC wrapping. That is met where clients meet the system: they call a notes module, an orders module, a signature module, each with workflow-shaped requests and events, and never an RPC. The identity service is separate and stateless.

Behind the API the measured constraints leave one honest design. A person's Broker connection answers one request at a time. The order-check session, the encounter cache and the locks live in the VistA job behind that connection. A second connection opened by token is a second job with its own state. So for each person, every module call runs through the same job in turn. The modules cannot be deployed, scaled or restarted independently, and none can serve two requests for one person at once. Version 1 drew fifteen service boxes, which promised more than this.

A cell scales by session. The constraint binds the modules inside one person's session. It does not bind one person's session to another's. So a cell is several identical session holders behind the gateway, which keeps each session on the holder that has its VistA job. Capacity grows by adding holders. A release takes one holder at a time: the holder stops accepting new sessions, its sessions end at their own sign-off or idle limit, and it is replaced. A session still open at a stated deadline goes through the restart case below, with notice to the clinician. A holder that fails takes only its own sessions into that case. Version 3 read as one process per VistA, which would have ended every clinician's VistA job at a site on every release.

Two layers of test

  • CPRS-shaped actions in the session core: opening a chart, loading an order dialog, accepting order checks, signing a note. Each is one thing CPRS does and is held to CPRS's recorded traffic under the written equivalence (functional calls, a stated CPRS state, timers and polls removed, record numbers normalized) ruled.
  • Module calls compose those actions. A composition with no CPRS counterpart, such as a team's overnight summary, is held to its own contract tests and labelled that way. A module can send an RPC only through an action.

The seam is the RPC call

Every RPC leaves the session core through one typed call: a name, parameters and a reply, described by that RPC's entry in the registry (§5). proposed

  • The rules apply there. The allowlist, the duty rules and the audit record are applied at that call. The web clients and CPRS coming through the Broker-protocol door pass the same check.
  • Each action declares the job state it depends on: the temporary globals and locks its RPCs leave in the VistA job, and the earlier actions that put them there. The registry marks which RPCs touch job state. The scan finds 161 used RPCs that touch job state and nothing else, and calls that write can touch it as well. An action that sends such an RPC and declares nothing fails the register's gate.
  • The restart replay is read from those declarations. The calls "that built job state" in the table below are then a list taken from the actions, and not one kept by judgment.
  • An action that declares no job state is proved from recordings, with no engine.
  • A back end could change here, one call at a time, checked by reply and database effect. A module is a workflow with its interpreter and its state, and it is not a unit that can be pointed at another back end. Version 5 named the module API as this seam.

Where unfinished work lives

CPRS keeps a half-written note and a half-filled order dialog in its own memory. With the interpreters server-side, that state lives in the session core, which appends each unsaved interaction to a journal keyed by person, patient and workflow. The browser holds view state only. Notes save to VistA on CPRS's own autosave schedule (§6). The journal holds clinical text in progress, so it is encrypted, never leaves the cell, and is deleted when the workflow ends. This is recommended, to be ruled before any write workflow. Two failures need different handling:

The size of a replay is measured. Of the 143 RPCs the order dialog engine names, 37 touch job state or locks and 20 write stored data. The alternative to a journal is a client data layer in the browser, as the new Teams has. It makes the browser the holder of unsaved clinical work and duplicates interpreter state on two sides.

What interpreter placement costs

With the interpreters in the session service, an answered prompt that changes what a dialog shows is a round trip from the browser to the cell. CPRS does that work in its own memory. How many round trips a dialog takes per answered prompt, and what they cost on a clinician's link, has not been measured. Production CPRS already takes half a minute to a minute to open one large template (§8). Phase 2 builds its thin path with the interpreter in the service, as recommended, and counts the round trips. Decision 11 is ruled on that count.

Where it runs

CPRS's traffic is chatty. The September review counted 36 calls in the patient-selection preamble, and in the 2026-09-28 recording of sign-on and list browsing, 138 recorded calls precede the first patient selection. Each person's session is a VistA process. So the session service runs as a cell next to each VistA instance, on the same network segment, and the browser reaches the cell over HTTPS. "Cloud" means the cells and the identity front door run in the same cloud as cloud-hosted VistA. They never sit across a wide-area link from the Broker. About 130 cells, each declaring a CPRS version and each with its own site's definitions, is an operations problem that belongs to track B and is not designed here.

A Broker-protocol door for unchanged CPRS

The session core's rules reach only the traffic that passes through it. A second door is proposed so that CPRS itself can pass through it, unchanged. Nothing of it exists. proposed

  • What it is. A listener on the session core that speaks the Broker's own protocol. CPRS is pointed at it in place of the Broker. For each connection it opens one connection to VistA and forwards the handshake and the sign-on as CPRS sent them. From then on it reads every call by name and parameters before forwarding it, and every reply before returning it. The person's VistA job, sign-on, keys and audit are what they are today. It forwards a call or refuses it, and it never answers in VistA's place. It is a router. It emulates nothing.
  • What it adds. The allowlist, patient binding and the service's audit record apply to CPRS's traffic, and to any other program that signs on with a person's codes through that port. Where a site can limit the Broker's port to the cell's address, the guarantees of §6 would cover all traffic with no VistA change. Whether a site can is a track B question (§17).
  • Observing first. In its first mode the door forwards everything and logs what each rule would have refused. That tests the allowlist and patient binding against every CPRS session on the box, where recorded clicking has so far reached 237 of the 1,067 RPCs. It also shows which patient-scoped calls CPRS itself makes outside the selected patient, before any rule is enforced on it. Refusal is switched on rule by rule, by ruling, once a rule's log is empty or explained.
  • The signature rule is a separate case. To apply duty 1 the door would send the validation call itself before forwarding a send. That is the one place it would speak to VistA unprompted, and it is ruled apart from the rest.
  • What is already here. CPRS in the Windows guest reaches vehu through the org's relay, which copies bytes and reads nothing measured. The door is that relay taught the protocol and joined to the session core. The operator's 2018 router did the parsing and the audit log in 857 lines over a protocol library (§8).
  • What it must not change. Bytes it does not refuse pass unaltered and in order. That includes the handshake's workstation name, which is what the sign-on log records read in code. The network address VistA sees becomes the cell's, as it is the relay's today. What Kernel's per-address sign-on limit and the production engine's licence count make of that is the question §10 and §14 already raise for the web path.
  • Limits. The Broker's port serves other applications too; the door applies rules inside CPRS's contexts and forwards and logs the rest. The duties CPRS applies itself stay CPRS's. The door needs its own ruling as a Broker door, with a retirement condition (§18; decision 21).

14Third-party and AI clients

The module API is what third parties use. Three measured facts shape how an agent may reach VistA:

  • Patient context belongs to the VistA job. Patient selection deletes the job's order-check session, encounter cache and allergy data (re-read in the code today). An agent selecting a patient inside the clinician's job would change the context under the clinician's screen.
  • A second job is not always allowed run live. With a person's multiple sign-on set to "not allowed", a second session as that person was refused. In the code every Broker sign-on runs the same check, the one-time token path included, and a third setting counts sign-ons per network address. On vehu 8 users have "not allowed".
  • Each extra connection has a cost. It is a process against the volume's ceiling. On the production engine the vendor's documentation says a licence unit covers up to 25 connections from one user and that past 25 the user consumes "one license unit per connection"; a user is identified by address unless the application names one, and neither Kernel nor the Broker does in this source. Through a service every connection past the 25th therefore costs a unit, where a workstation's extra connections were free.

The reference factory

  • A scenario is a script. Each step names a form and a control, as CPRS's form files name them, and the calls it expects, as the existing helper's expect step does. Nothing in it is a pixel position.
  • One script drives three things: CPRS through the guest driver, classic mode through a browser, and the session service through its API. Classic mode is generated from CPRS's form files, so a control has the same identity in both clients.
  • Every run starts from a restore point. The copy is put back to a named state before CPRS starts. CPRS's saved window places and preferences go back with it, because CPRS keeps them in VistA read in code.
  • CPRS run against itself sets the set-asides. Whatever differs between two CPRS runs of one script, such as the clock, a process number or a counter TaskMan moved, is what a comparison sets aside. Anything else is a difference, and a difference goes to a ruling.
  • The candidate starts from the same restore point as the reference it is compared with, so record numbers agree wherever the writes agree.
  • The recorder also times CPRS. The calls and seconds CPRS itself takes for each answered prompt are what the round-trip count of decision 11 is set beside.
  • The factory is how the reference is made again: for a new CPRS build, a new patch level, foia, or another site's exported definitions. The entries that change name the rows to re-read.
  • It never touches gold. Every run is on a throwaway copy.

Three things in CPRS make this plausible, and none has been tried. Its forms are text and name every control. Delphi's library registers a form's window under its class name known of the library; not checked here. And the Broker's source has two silent sign-on routes, one taking a sign-on handle from the command line and one taking the codes without the form read in code.

How a row is proved

A row counts as built when a machine can check all of the following on the commit.

  1. It cites its source: units and routines that exist in the pinned CPRS tree.
  2. It disposes of candidates: the bindings, call sites, messages and access tests it covers are named. A candidate that no row names is red for the register.
  3. It names its references: entries in the bank, current for the declared CPRS build and copy.
  4. It names its tests, and each test declares the oracles it applies. The gate derives the kinds the row needs: traffic if it cites an RPC, the database if any of those writes, text if it produces clinical text, the window tree if it shows a screen, a refusal if it is a duty.
  5. Each test was seen to fail before the code that satisfies it existed, and the record is kept. A nightly sample plants faults in the code a row cites, and a row whose tests catch none is listed.
  6. Each test passes on this commit: from the bank, with no engine, in the repository's gate; and live on the lane's copy each night.
  7. Each remaining difference from CPRS carries its ruling.

The headline number of §11, rows proven over rows, is then computed from records a gate has checked. A page for each row, generated from those records, is what the operator reads when a row is questioned.

Parallel work

  • The factory runs alone, unattended, at all hours. There is one guest, and the host has room for one more at most: 27 GB, with 7 GB free while one guest runs measured. Its queue follows the longest chain of §15: the order actions, the dialog base, order management.
  • Reading fans out at once. A source read of one unit into candidates and rows is read-only and independent of every other. It needs no lane and no contract. Each engine is read twice, independently, and the overlap of the two reads estimates what both missed.
  • A lane's inner loop needs no engine and no guest. It runs from the bank. The live proof runs nightly on the lane's own copy, which costs a 3.4 GB file and about 110 MB of memory measured.
  • The shared files are kept by track: one register file, one registry file and one bank directory for each, joined by a generator.
  • The operator is given a queue. A row whose evidence the gate has checked is not reviewed one by one; a sample is. Differences come in batches, each with CPRS's side and the candidate's.
  • A lane is added on measurement. The first track records the operator's minutes and rulings per row, and decision 23 is ruled on those. Six lanes at twenty rows a day, at Loupe's rulings per row, would be near a hundred rulings a day projection.

Reliability

  • A scenario is admitted to the bank after two runs from one restore point agree.
  • A scenario seeds the state it needs on its own copy, and depends on no other scenario.
  • A step is checked by the calls it caused, and never by a picture alone.
  • A live failure is counted and printed. It is never retried in silence.
  • A missing reference, journal or tree reds the row. It is never skipped.
  • A copy runs under a fixed clock if the trial of that holds. Until then the clock is a measured set-aside.
  • The tap stays as the cross-check on the wire recorder, and CPRS's own RPC log is a third.

Phase 0's exit tests for the factory

  1. One scenario runs from a restore of the copy to CPRS's exit with nobody at the keyboard.
  2. Run twice, it gives two entries that agree in trace, journal slice, window trees and text, once the measured set-asides are applied.
  3. A planted difference of each kind is caught: a changed parameter, an extra write, a changed caption, a changed character of text.
  4. The wire recorder and the tap agree on one scenario, but for the named line.
  5. The planner lists every unrecorded RPC with where to record it.
  6. The rate is written down: scenarios an hour, and the operator's minutes per scenario, which should be none.

If a test cannot pass, the reason is measured and written into §17, and the calendar of §15 is restated at hand speed. That is decision 27.

Limits

  • Most of this is untried: driving CPRS from inside the guest, unattended sign-on, the wire recorder, a restore fast enough to run before every scenario, journaling the temporary globals, a fixed clock, the line trace. §17 lists each with what would settle it.
  • The factory proves CPRS on demo data, on one build. It says nothing about a production site.
  • CPRS run against itself shows what cannot be demanded. It does not show which of the things that agree are required and which are incidental. That stays with the written equivalence and the operator's rulings.
  • The generators narrow. A reader still decides what a row is.
  • Building tools is work that could run on. Each starts from something Loupe already runs, and phase 0's exit tests are where it stops.
