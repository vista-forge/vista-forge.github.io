Round 3 verdict

Emulating VistA's RPCs as a service would not be the better route. It rebuilds the half of the system that version 3 keeps, and it does not produce a web client. The operator asked whether the RPC emulation service begun in 2016–2019 would be technically better than this plan, judged on what is maintainable, executable, pragmatic and scalable for a cloud-based CPRS service. The archive was measured in its code, where version 3 had read only its READMEs.

  1. The two approaches rebuild opposite halves. Version 3 ports the Delphi client and calls VistA's rules unchanged. Emulation keeps the Delphi client and rewrites VistA's side of every RPC. A web client would still have to be built afterwards, so for this request emulation is extra work and is no substitute.
  2. The archive's emulation server holds 152 RPC models, and 141 of them are among the 1,067 RPCs CPRS uses (13%). Sixteen change data: five problem-list calls, four vitals calls, one allergy save, five preference saves and a division switch. Nothing was emulated for orders, notes, encounters, consults, signature or order checks.
  3. Measured by the M code behind them, the emulations covered under a tenth. The emulated RPCs reach 14,286 lines of M, 9.5% of what CPRS's used RPCs reach. 136,119 lines are reachable only from RPCs that were never emulated.
  4. The project fielded its monitor, not its emulator. The second-year work delivered a passive monitor of RPC traffic that needed no change to VistA or to any client, received its authority to operate and ran in production at one site in January 2020.
  5. The archive's router design and its hand classification of CPRS's RPCs are worth taking. A door on the session core that speaks the Broker's own protocol would put unchanged CPRS behind the same rules as the web client. That is the piece of the earlier work that version 3 lacks.
  6. Version 3 remains the right core. Four gaps the first two rounds did not test are in §E6, and the changes are in §E7. Version 4 of the plan carries them.

E3Why emulation carries the larger risk

  • VistA's RPCs are not the end of the line. CPRS is one client of VistA's database. Pharmacy, laboratory, radiology, billing, HL7 interfaces and background tasks work on what CPRS's calls file. The order send call has 41 global roots in its reach, across those packages measured. An emulator outside VistA must reproduce every one of those writes into VistA, or the departments never see the order. The first design avoided a second store by writing VistA's own files through FileMan and, in places, direct global writes archive. That fires cross-references and skips the package code that normally files the record.
  • The proof compared replies and not effects. The remote tests say "other than datetime differences, all replies should be the same" archive. The router compared the two reply buffers on calls sent to both systems and, on a mismatch, logged "VICS and VistA output do not match on fanout, shutting down connections" measured. Calls that change data were sent to both systems. A reply can match while the audit entry, the alert or the pharmacy record is missing.
  • A second store needs every VistA's data, continuously. The archive's own notes call the reduced data set "the amount of data that needs to be synchronized between a VISTA and National Services" archive. Version 3 has no migration and no synchronisation, because both clients use the same VistA.
  • The interface moves, and the server moves behind it. The project's 2017 list of CPRS's context has 1,050 RPCs. vehu's has 1,190 today: 1,036 are in both, 14 are gone and 154 are new measured, on two different VistA instances. An emulator owes those 154, and it also owes every change a patch makes behind a name that did not change. Such a change is invisible at the interface. A client port owes the same 154 on the client side, where a miss shows on the screen.
  • What emulation would buy is real and is not this request. A stateless JavaScript tier scales out more easily than one VistA job per person, and it is the only route that survives VistA being switched off. The request is a web replacement for CPRS over VistA. Version 3's module API is the seam where a module could later be pointed at another back end, one module at a time, if that ever becomes the goal.

E5What the plan should take from the archive

Neither item exists in this org. Both are proposals.

  • A Broker-protocol door on the session core. Version 3 says its guarantees "cover traffic through the service; with no change to VistA, the Broker stays open to CPRS itself". The archive's router sat between CPRS and the Broker, parsed every call, kept an audit log and decided where each call went; its security study lists per-RPC parameter checks and "invalid patient for session". The same door on the session core would apply the allowlist, patient binding and the audit to unchanged CPRS. Where a site can limit the Broker's port to the cell's address, the guarantee would then cover all traffic with no VistA change.
    • On this box CPRS in the Windows guest already reaches vehu through the org's own relay (v rpc relay), which copies bytes and parses nothing. The door is that relay taught the protocol and the session core's rules.
    • It should first run in an observe-only mode that logs what it would refuse. That tests the allowlist against every CPRS session on the box. Recorded clicking has reached 217 of the 1,067 RPCs so far.
    • It needs its own ruling as a Broker door, with a retirement condition.
  • The 2017 hand classification as a second source for the registry. Version 3 takes each RPC's effect class from round 2's scan, which it calls a first cut. The archive's 2017 breakdown classed the 1,050 RPCs of CPRS's context by hand as read, change or utility, with tags for alerts, bulletins and locks; 1,036 of them are still in the context. The two disagree on 129: of 744 RPCs the breakdown calls reads, the scan finds a stored write in reach of 116 (3 of them only in scratch globals), and of 145 it calls changes the scan finds no stored write for 13 measured. Neither is proof. Each disagreement is a place where the plan's database comparison should look first.
    • The later definition of all 6,385 RPCs, a 2019 deliverable, is not on this box: its file is an 18.5 MB large-file pointer that was never fetched. It was not read.
  • Nothing else needs taking. The archive's sniffer, sequence runner, load tester and Broker simulator have counterparts in the org's tap (capture, drive, load, fixture).

E6What rounds 1 and 2 did not test in version 3

  • Scale inside a cell missing. §9 says the modules "cannot be scaled or restarted apart", which is true of modules. It never says that sessions of different people are independent. As written, one deployable per VistA reads as one process, and every release would end every clinician's VistA job at that site at once. The cell should be several identical session holders behind a gateway that keeps each person on one of them, released one holder at a time as its sessions end.
  • The reference client is driven by hand missing. Write rows need CPRS operated in the Windows guest. At Loupe's pace of 57 built rows in the eight days from its first commit, read-only, 3,200 rows is about 450 days, and write rows are slower projection. Scripted driving of CPRS would turn the oracle from hand speed to machine speed, and phase 0 has no row for it.
  • No measurement behind running the interpreters in the service unsupported. Decision 11 puts every dialog interaction through a round trip to the cell. The archive's site note shows production CPRS taking between half a minute and a minute to open one large template. Phase 2 should count round trips per answered prompt before decision 11 is ruled.
  • §8's account of the archive rests on READMEs corrected. It gives 345 files and 155 entries and says the READMEs do not explain the stop. The figures in §E2 replace it.

E7What should change in version 3

  1. Replace §8's archive entry with the measured figures, and record emulation of VistA's side as declined, to be reopened only if a site has no VistA to call.
  2. Add a decision: a Broker-protocol door on the session core, observe-only first (§E5).
  3. State in §9 that a cell scales by session, and add a rolling release to phase 2's exit test (§E6).
  4. Give the RPC registry a second source column from the 2017 hand classification, and list the disagreements (§E5).

Round 2, on version 2 of the plan

What follows is the second review, unchanged. Its ten changes were folded into version 3 of the plan.

Round 2 verdict

The plan's two central safety claims are no longer code readings. They were run, on a throwaway copy of vehu, and both are true. VistA signed an order, and released a discontinue, on a signature code it had just declared invalid. It let a user whose write access is "no" create a note and sign an order. Round 2 also built a label-level scan of the M code, stress-tested version 2's own new measurements, and checked four outside claims against primary documents.

  1. Order signing does not check the code measured. ORWU VALIDSIG answered 0 for a made-up code. ORWDX SEND with the same code answered "signed" and filed the signature. A second send released an unsigned discontinue and the lab order became discontinued. A note signature with the same code was refused.
  2. Write access is not enforced by the server measured. With Notes and Orders set to "no" for a user, the server reported the restriction to the client, then created the note and signed the order when asked.
  3. The server serves any patient to a user restricted to a patient list measured. This exposes a rule version 2 lacks: every patient-scoped call must name the patient the session selected and checked. 217 of the RPCs CPRS uses take a patient parameter, and 107 of those write.
  4. Locks vanish within three seconds of a dropped connection measured, and hold while the session lives. Version 2's work-in-progress journal is therefore a replay protocol: after a restart the locks are gone and may be held by someone else.
  5. A second job for the same person is refused where multiple sign-on is not allowed measured. That blocks version 2's "agents get their own VistA job", and the web client beside CPRS, for those users.
  6. The M behind CPRS's RPCs is about 157,000 code lines in 2,637 routines by a label-level scan, with FileMan not entered and 2,407 indirection sites unresolved. This replaces the 37,000-to-a-million range.
  7. Version 2's "six interpreters" is fragile. Three sit exactly on the threshold. Only two survive every variant of the test.
  8. Version 2's allowlist holds against everything recorded (217 of 217 RPCs), with two gaps: RPC names passed inside remote calls, and add-in calls among the "unused" set.

Three round-1 statements are refined in §T8: keyboard parity has a third route, the licence concern is narrower than stated, and controlled-substance signing has a confirmed audit requirement. The changes for the plan are in §T9, and version 3 of the plan carries them.

T4Version 2's allowlist, tested

Version 2 defines the allowlist as the 1,067 RPCs CPRS and its Vitals DLL use, and refuses the 166 others the context admits.

  • It holds against everything CPRS was recorded sending holds. The September tap list and every committed recording through 2026-09-28 name 217 distinct RPCs. All 217 are inside the used set.
  • Remote calls carry an RPC name inside a parameter missing. Five call sites send XWB REMOTE RPC with the RPC to run at the other site as an argument: one literal (ORWCIRN RESTRICT) and four that pass a variable supplied by the Reports and Labs tabs. An allowlist that checks only the outer name passes any inner name.
  • The "unused" 166 include writers that an add-in may send missing. 37 of them write stored data. Among them are a mental-health save and results call and an imaging import. No CPRS unit names them, and who sends them is unknown: an add-in without source, or nobody. Refusing them by default is right. It also means an add-in may not work through the service until its calls are recorded and admitted.
  • The allowlist is per site. Eight of vehu's used names come only from its report definitions. Another site's definitions name others.
  • A name list is not enough missing. Test G shows the server answers for any patient number. The session core has to hold the selected, checked patient and refuse a patient-scoped call that names another: 217 used RPCs take a patient parameter by name, a lower bound, and 107 of them write stored data. The security study in the operator's archive listed the same check ("invalid patient for session").

T5The work-in-progress journal is a replay protocol

Version 2 recommends that the session service journal each unsaved interaction "so a restarted service or a reloaded page can rebuild the dialog". The measurements say what rebuilding involves.

The classes overlap, since one call can do both. After a restart the VistA job is gone, and with it its temp globals and its locks (test C). Rebuilding a half-filled order dialog means re-sending the state-building calls in order, never re-sending the ones that write stored data, and re-taking a lock that someone else may now hold. A reloaded browser page is easier, because the job is still alive. Version 2 treats the two cases as one.

Fix: specify the two cases apart. For a restart, say what the clinician sees when the lock cannot be re-taken, and add that case to phase 2's exit test.

T6Agents, second jobs and licences

  • Multiple sign-on measured. Test F: a second session for a person whose setting is "not allowed" is refused. In the code, every Broker sign-on path runs the same check, the one-time token path included, and a third setting counts sign-ons per network address. On vehu 8 users have "not allowed" (measured in September). For them an agent cannot have its own job, and the web client cannot run beside CPRS.
  • Patient context. Re-read today: patient selection deletes the job's order-check session, encounter cache and allergy data. Round 1, on version 1 of the plan

What follows is the first review, unchanged. Its thirteen changes were folded into version 2 of the plan. Where round 2 has since measured or corrected a point, the round 2 section says so.

Round 1 verdict

The direction stands. The plan should not be ruled as written. Calling VistA's rules instead of rewriting them, interpreting each site's definitions, running every call as the signed-on person and holding the new client to CPRS's recorded behaviour all survive this review. Most of the plan's counts reproduce, and three attacks on its census failed outright (§2).

Seven findings change the plan:

  1. The fidelity metric can reach 100% while the product is wrong. Its unit is the Delphi routine, and single routines run past 1,100 lines. Its "definitions rendered" gate has no CPRS output to compare against except where CPRS was recorded. Its RPC count is by name, while 89% of RPCs are called from one place and vary only in their parameters. The org already has a working unit the plan ignores: Loupe's register of one CPRS capability per row, each proven by a test or closed by a ruling (§4).
  2. The plan missed a client-side permission engine. uWriteAccess.pas decides whether a person may write, by 18 areas and 24 actions, at 174 call sites in 34 units. The five server routines behind order, note and encounter writes never consult those rules. This is the mechanism that makes CPRS read-only at a site moved to the new EHR (§5).
  3. The "domain services" are modules of one stateful session holder. A person's Broker connection answers one request at a time, and workflow state lives in that VistA job. The services cannot run, scale or fail independently, and the plan never says where unfinished work lives (§7).
  4. AI and third-party clients cannot safely share the person's session. Patient context belongs to the VistA job, so an agent selecting a patient changes it under the clinician. A draft order saved to VistA is a real unsigned order (§7).
  5. Classic mode cannot be faithful in a plain browser tab. 29 of CPRS's 244 keyboard shortcuts use keys a tab will not release, including Ctrl+N (Notes tab) and Ctrl+T (Consults tab). The "optional" desktop companion is required for keyboard parity (§6).
  6. Two claims about vehu were wrong or unsupported. vehu has no usable printer, so none of the 22 print RPCs can be tested there. The "about 45 calls for a cover sheet" figure cannot be derived from the recordings (§3).
  7. The plan has no effort estimate and blurs two projects. A reference implementation proven on demo VistA is something this org can build. Deployment at VA depends on approvals, licensing and data volumes that nothing here can measure. Only 21 of the 1,190 RPCs are marked public (§9).

The fixes are listed in §11. None requires new architecture. Most are a change of unit, a missing row, or a claim reduced to what was measured.

4The metric can read 100% on a wrong product

The plan's §11 promises a "deterministic, measurable" fidelity number. Six defects let that number reach 100% without the product being faithful.

4.1 The routine is the wrong unit

The plan gives each Delphi routine one disposition. Routine sizes make that too coarse where it matters most measured:

  • The median routine is 10 lines. The 998 routines of 50 lines or more (7.3%) hold 37.7% of the code, and the 252 of 100 lines or more hold 18.3%.
  • TfrmLabs.tvReportsClick is 1,258 lines and TfrmReports.tvReportsClick is 1,101. Each is one event handler that interprets every report definition type. "Ported: yes" for either hides dozens of separate behaviours.
  • Nested helper routines split their parents, so some dispositions would attach to fragments.

The org already has a unit that works. Loupe's internal/coverage/signon-selection.tsv holds one CPRS capability per row, read from the source and the first recording. Each row is built (evidence: the tests that prove it), not built, or ruled out (evidence: the ruling), and a test gates the table against the repository. Seventy-five rows carried sign-on and patient selection to a passed side-by-side test on 2026-09-29. The plan never mentions this register and invents a different unit measured.

Fix: make the capability row the unit of proof, derived engine by engine from a source read. Keep the routine census as a completeness check: every routine maps to at least one row, or to a named non-behaviour class.

4.2 "Presentation" is a cheap exit

The plan lets a routine count as replaced when "a classic-mode screenshot comparison … reaches the form". About 2,370 compiled routine bodies (17%) sit in the control library and the accessibility framework alone. One screenshot per form would clear most of them. The control library is where CPRS's sorting rules, incremental list paging and date entry live, and the plan itself says those "are carried exactly". A screenshot proves none of that.

Fix: a control class counts when its behaviours are rows with tests (keyboard, paging, sorting, date parsing). A screenshot proves layout only.

4.3 "Definitions rendered" has no CPRS output to compare against

The plan gates each engine at "100% … parses, renders and round-trips to the same response strings as CPRS … over the site's whole census". CPRS's output exists only where CPRS was driven and recorded. For 5,837 templates and 10,099 reminder elements, nothing produces CPRS's rendering of each one. Driving CPRS through each in the Windows guest is the only source, and the plan gives no method or budget for it. As written, the gate can only prove that the new interpreter accepts every record.

Fix: two gates with different names. Accepted: the interpreter parses the whole census with no unknown construct. Matched: every feature of the definition grammar (field type, prompt type, nesting, object, required flag) is exercised by at least one case recorded in CPRS. The second is finite and can be planned.

4.4 RPC coverage is by name; variation is in the parameters

965 RPCs have a parsed call site in compiled code. 856 of them (89%) are called from exactly one place, and only 29 are called with more than one argument count measured. CPRS wraps each RPC once and varies what it sends. ORWDX SAVE files every kind of order through one call site. One scenario would mark it "delegated" although it covers one dialog type of dozens.

Fix: for RPCs whose behaviour depends on a parameter (the save, sign, lock and dialog-definition calls first), list the parameter classes and count each class, not the name.

4.5 The denominators are not the populations the request named

  • RPCs: the request says "the RPCs that Delphi CPRS uses". The plan counts the 1,190 the context admits. 191 of those are never named by the client and 136 have no explanation. Each would need a ruling to leave the "unknown" class, and the plan does not say who makes 191 rulings or on what evidence. RPCs sent in other contexts (the Vitals DLL's, the mental-health DLL's, Event Capture's) are outside the count.
  • Delphi code: the count excludes the Vitals client, whose source is on this box and which the plan says to port: 73 units, 32,995 lines, 42 forms measured. It also excludes the screen-reader framework's own DLL project.
  • Site definitions: "25,000+" is not a number a gate can test. The table beside it sums to 27,705 with orderable items and leaves out business rules, encounter forms, health-summary types and parameter values.

4.6 It is deterministic only after someone assigns 13,625 dispositions

The registry is generated, but each disposition is a judgment, and the plan names no rule or reviewer for making it. Two honest reviewers would classify a 300-line event handler differently. A metric whose inputs are unreviewed judgments is repeatable, and it is not objective.

4.7 The plan quietly changed what "coverage" means

The request asks for "objective coverage of 100% of the delphi code". The plan gates on dispositions and only reports how much of CPRS the scenarios execute, and that report needs a rebuild of CPRS that has not been tried. The reasoning is sound: error paths cannot all be executed. But it is a change to the stated requirement, and the plan presents it as a definition. It should be put to the operator as a decision, with the alternative named: an execution floor per engine, set after the first engine shows what is attainable.

5Duties and engines the plan missed

5.1 Write access: a permission engine in the client missing

Measured and read in code today.

  • uWriteAccess.pas (1,140 lines) defines 18 write-access areas (orders, progress notes, consults, medications, problems, allergies, encounter, immunization, vitals, delayed orders and others) and 24 actions (write, copy, change, renew, hold, discontinue, sign, release without signature, verify, transfer, park and others).
  • Client code tests it at 174 call sites in 34 units.
  • The rules come from VistA: ORACCESS GETNOTES and the system-parameters call in ORWU. The documentation names the parameters OR CPRS TABS WRITE ACCESS, OR CPRS ORDERS WRITE ACCESS and OR CPRS OTHER WRITE ACCESS, which let a site "control whether or not a user, a division, or the entire system (site) is allowed to write orders". vehu holds 7, 60 and 7 values for them.
  • The server routines behind the main writes (ORWDX, ORWDXA, ORWDXR, TIUSRVP, ORWPCE2) contain no reference to the access routine. Six other routines do: ORWU (to hand the rules to the client), ORCB, ORCHART, TIUALRT, PXRMEHR, and one check in ORWDX2 for a site that has moved to the new EHR.
  • A companion parameter, OR SIMULATE ON EHR, exists to test behaviour "as if the site migrated to an Electronic Health Record (EHR) system".

So by the code, the restriction that makes CPRS read-only at a migrated site, or for a restricted user, is applied by the client. A web client that skips it would let those people write. The plan's duty table has no row for it, and its engine table hides the unit inside "application shell". Whether the server refuses such a write was not tested live. It belongs in the duty register directly below order signing, with its negative scenario on a throwaway copy.

5.2 Duty candidates dropped on the way from the surface map

  • Inactivity lock-out. CPRS counts down and closes on idle (fTimeout). The plan's keep-alive rule covers the VistA session and says nothing about locking an unattended browser.
  • Note autosave. Notes, consults, discharge summaries and surgery reports save on a timer set from the person's autosave interval (5 minutes by default). A web client that saves at other moments changes what a crash loses and what other people see as unsigned drafts.

7The services are one stateful session holder

The request asks for "a service based architecture, not piecemeal wrapping of RPCs". The plan answers with fifteen service boxes over an equivalence layer. The measured constraints make that picture misleading.

7.1 Fifteen boxes, one process per person

A Broker connection answers one request at a time, and workflow state lives in the VistA job behind it: the order-check session, the encounter cache, the locks (carried from the September reviews). So every "service" call for one person goes through the same connection in sequence. The services cannot be deployed, scaled or restarted independently, and none can run two requests for one person at once. Opening a second connection by token gives a second job with its own state, which splits a workflow across jobs. What the plan describes is one session service with domain modules. That is a sound design. The diagram and the word "services" promise more.

7.2 Nowhere for unfinished work to live

CPRS keeps a half-written note and a half-filled order dialog in its own memory, and autosaves notes on a timer. The plan moves the interpreters server-side and gives the browser only a cookie. It never says where a half-filled order dialog lives. If in the session service, a restart of that service loses every clinician's work in progress at once. If in the browser, a refresh loses it and the server-side interpreter has to be rebuilt from client state. Microsoft's account of the new Teams, as summarized in search, describes a client data layer running in a worker for this class of problem external. The plan needs a ruling on state placement before any write workflow.

7.3 Agents cannot share the person's job

The plan has third-party and AI clients call "in that person's Broker session". Patient context belongs to the job: selecting a patient clears the job's order-check, encounter and allergy caches (measured in September). An agent that selects another patient changes the context under the clinician's screen. Giving each agent its own job by token is the alternative, and it counts against the volume's process ceiling and against Kernel's multiple-sign-on setting. The plan addresses neither.

7.4 A "draft" order is a real order

The plan says "agents draft; people sign". Saving an order in VistA creates an unsigned order in the ORDER file. Other people see it, and it raises unsigned-order alerts. Order checks fire when the dialog is accepted and may need an override reason from a person. So a draft that reaches VistA has clinical effects before anyone signs. The plan should rule where agent drafts are held: in the session service until the person accepts each one, or in VistA as unsigned orders with their consequences accepted.

7.5 The per-site census gate contradicts "no service identity"

The plan gates each engine on rendering "the site's whole census" of definitions, per site. It also rules that no call ever runs under a service identity. On vehu the census is read through the driver stack, which does not exist at a real site. Reading ten thousand reminder elements there needs some identity. The plan has to choose: an administrator's read-only export, a ruled exception, or no per-site gate.

7.6 "Enforces the duties" holds only for traffic through the layer

The abstract says the layer "enforces the duties VistA leaves to the client". With no VistA change, the Broker stays open to CPRS and to any program with a person's codes. The September review said so; the plan dropped the qualification. The guarantee is a policy for the org's own clients.

7.7 One cell per VistA, about 130 times

A cell beside each VistA, each declaring a CPRS version and each passing census gates on its own site's data, is roughly 130 deployments and 130 gate runs per release. The plan states the shape and none of the operations: who runs the gates, on what data, and what a red gate at one site does to the release.

9Scale, governance and what can be proven here

  • There is no effort estimate. The plan has ten phases and no size for any of them. The one in-house data point: Loupe went from its first commit on 2026-09-22 to 351 commits, 32,005 lines of code and 22,793 lines of tests by 2026-10-03, and in that time carried sign-on and patient selection (75 capability rows, read-only) to a passed side-by-side test measured. The Delphi behind patient selection is 5,320 of 355,291 lines. Writes are slower than reads: each needs a throwaway copy, CPRS driven by hand in the Windows guest, and a database comparison. The plan should size at least phase 1 in rows before it is ruled.
  • Two projects are written as one. A reference implementation, held to CPRS on demo VistA, is within this org's reach and its rules. Deployment at VA is a different project: identity-provider registration, a Kernel change, production data volumes, accreditation. The plan moves between them without saying which claims belong to which. Nothing about the second can be tested on this box.
  • RPC governance. VistA marks each RPC's availability. Of the 1,190 in CPRS's context, 21 are public, 257 are subscription, 105 restricted, 9 by agreement, and 798 carry no marking measured. A client other than CPRS that depends on 1,169 non-public RPCs has a permissions question at VA that the plan does not raise.
  • The target route for identity depends on a change VA has not been asked for. The plan lists this under unknowns. It should also say plainly that until then the working route at VA is the SAML token path that VA's own web applications use, and that the plan's sign-on design for VA is that path.
  • Licensing on the production engine is unexamined. VA's VistA runs on InterSystems' engine, which counts licence units per connecting user. A middle tier makes every clinician arrive from one address. Whether that changes licence consumption is general knowledge about the product and was not measured here.
  • Controlled-substance signing is a regulated function. The plan treats PIV signing as a companion feature. Federal rules for electronic prescribing of controlled substances place requirements on the signing application itself. That was not researched and should be listed as an unknown.
  • CPRS keeps changing. The plan pins one build and calls a new one "a regeneration". Only one snapshot of the source is on this box (the mirror's history is a single commit), so the size of a release-to-release change is unmeasured.
  • The build notes in the mirror are for an older CPRS. They describe Delphi 2007 and digital-signature files fetched from a separate repository. The plan's "the tree looks buildable" rests on the project file alone.

10Order of work

The plan builds every read screen, then notes, then encounter and reminders, and reaches orders in phase 5. Orders hold the plan's largest risks: the biggest interpreter (48,241 lines), the order-check session state, the unenforced signature, write access, and the agent question. Leaving them to phase 5 means the architecture is proven late.

Fix: after the session guard, run one thin path end to end on a throwaway copy before widening: one quick order, through order checks and signature, with the wrong-code and write-access refusals. It needs no classic-mode generator and little screen work. It settles state placement, the duty rules and the equivalence method while they are still cheap to change. The parked service-layer proposal had orders at its phase 3 for the same reason.

13How each number was taken

  • Routine bodies and sizes: headers after implementation, excluding those inside type declarations; size is non-blank lines to the next header, so a routine with nested helpers is split at each helper.
  • Behaviour signals: per compiled unit, constructor calls on visual control classes; Piece( and Pieces( calls; the four RPC call forms.
  • Shortcuts: ShortCut = n in compiled forms, decoded to key and modifiers, compared with two fixed lists of browser keys.
