Use your AI assistant

You already use an AI coding assistant. This page gets it working on M code in this box in a few minutes, with the credentials you already have. Pick your assistant below and follow its steps; then do the first task at the end, which takes about five minutes and proves everything is wired.

How it works, in one paragraph

Section titled “How it works, in one paragraph”

Your assistant does what you would do: it edits the files in your project and runs m test, m lint and the other m commands. Two things make it good at M from the first minute. The box carries a one-page contract, /opt/docs/AGENTS.md, that tells any assistant what the box is, the commands, the project shape and the rules; and it carries the standard library and the house style as knowledge the assistant can read (/opt/msl/skill, /opt/docs/skills). Cline, the assistant built into the IDE, already has the contract loaded. Any other assistant gets it by copying one file into your project. That is the whole setup.

Cline, the assistant built into this IDE

Section titled “Cline, the assistant built into this IDE”

Cline is an open-source coding agent installed in this IDE. It works with Anthropic, OpenAI, Google, OpenRouter and many other providers, and with a local model. It already knows the contract.

  1. Click the Cline icon in the left activity bar (a robot). If you do not see it, press Ctrl+Shift+P, type Cline, choose Cline: Open In New Tab.
  2. On the welcome screen, choose your API provider from the list and paste your API key. Pick a model. (Anthropic: a key from console.anthropic.com. OpenAI: platform.openai.com. OpenRouter: one key, many models.)
  3. Look at the bottom of the Cline panel: a switch reads Plan / Act. Leave it on Act for the first task.
  4. Above the chat box, open Auto-approve and tick Read project files and Execute safe commands. Leave Edit project files unticked for now, so you approve each edit.
  5. Type your first task (below). Cline will read the contract, read the files, propose edits for you to approve, and run m test in the terminal. You will see every command and its output.

Your key lives in this container's IDE state. A fresh docker run --rm starts clean and asks for it again; a mounted user-data volume keeps it.

Your desktop editor edits the files on your host; the box runs them.

  1. Start the box from the project directory and install the m shim, as in the Claude Code steps 1 and 2.

  2. Put the contract where your editor's assistant reads it:

  3. Open the project folder in your editor. In its integrated terminal, m test tests works because the shim is on your PATH; your assistant runs the same commands.

Gemini CLI, Aider, and everything else

Section titled “Gemini CLI, Aider, and everything else”

Any assistant that can read a file and run a command works the same way: the m shim on your host (Claude Code step 2) and the contract in the project under the name your assistant reads (GEMINI.md for Gemini CLI, AGENTS.md for most others, or paste the contract into its first message). Aider: aider --read AGENTS.md.

A local model instead of a key

Section titled “A local model instead of a key”

Run Ollama or LM Studio on your host, then in Cline choose that provider and set the base URL to http://host.docker.internal:11434 (Ollama's default). On Linux, add --add-host=host.docker.internal:host-gateway to the docker run line so the container can reach your host; Docker Desktop on macOS and Windows provides that name by itself. No key, no cost, and nothing leaves your machine. A small local model will need more guidance than a hosted one; the first task below is within reach of a 7B coding model.

Your first task, step by step

Section titled “Your first task, step by step”

This takes five minutes and exercises the whole loop: read the contract, write a test, see it fail, implement, see it pass, lint.

  1. In the box's IDE, open the examples folder → hello. (With a host assistant, use your own project, or copy the example: docker cp m-devbox:/opt/examples/hello ./hello.)

  2. Give your assistant this, word for word:

    Add a label greet(name) to src/HELLO.m that returns "Hello, <NAME>!" with the name upper-cased using the standard library. Work test-first: add the test to tests/DEMOTST.m, show me it failing, then implement and show me it passing, then lint.

  3. Watch for these four things, in this order. Each one is a command the assistant runs and you can see:

    Step The command it runs What you should see
    it writes the test first m test --expect-red tests "verdict": "assert-red" and exit 0 — the test ran and failed on its assertion, which is the point
    it implements greet (edits src/HELLO.m, using $$toUpperASCII^STDSTR) a few lines added under a new greet(name) label
    it proves it m test tests "verdict": "assert-green", passed one higher than before, failed: 0
    it cleans up m lint --error-on=error src tests and m fmt src tests no findings; no changes

  4. Open src/HELLO.m and look at what it wrote. Then press Run Code (▷) on the file: the top label prints its greeting on the engine.

If the assistant skipped the red run or went looking for a mumps command, it did not read the contract. Check the file is where its steps above put it, start a new conversation, and try again.

Three more tasks

Section titled “Three more tasks”

A small tool from a data file.

Look at /opt/examples/csv-report first. Then, in a new project ORDERS scaffolded with m new ORDERS, read data/orders.csv with STDCSV and print the total amount per customer as JSON, sorted by customer. Test-first, one test per behaviour.

Expect: m new ORDERS creates the three files, a copied data/orders.csv, a suite that grows one test at a time, and $$toJSON^STDJSON in the output. Ask it to run m coverage src tests --min-percent=85 at the end.

Find out why a suite is vacuous.

This project's m test tests says vacuous, 0/0. Find the cause and fix it.

Expect: it finds that .m-cli.toml lacks [dependencies] routines = ["src"], adds it, and the suite runs. (The contract explains this; a good assistant finds it in one step.)

Package and install what you built.

Turn src/ into a library named orders: write dist/orders-manifest.json naming its routines, install it with m lib, verify it, call it with m engine exec, then uninstall it and prove the engine is back where it started.

Expect: m lib install --name orders src, m lib verify orders reporting ok: true, one m engine exec line, m lib uninstall orders, and m lib list no longer showing it. bash /opt/examples/lib-demo/tour.sh does the same cycle on a tiny library if you want to see it first.

It is working when

Section titled “It is working when”
  • m engine status from wherever the assistant runs reports healthy.
  • The assistant's first act on a task is to read the contract (Cline: you see .clinerules or the global rule; a CLI: AGENTS.md/CLAUDE.md).
  • It runs m test --expect-red before it implements.
  • It calls the standard library by name ($$…^STD…) instead of writing its own string, JSON or date code.
  • It never types mumps.

If something is off

Section titled “If something is off”
You see Why Do this
a run-lock refusal on m test the engine is single-writer and the IDE's status chip, a m watch, or another terminal held it for a moment tell the assistant to run the command again; once is always enough
vacuous, 0/0 no [dependencies] routines = ["src"] in .m-cli.toml ask it to add that line (or start projects with m new, which writes it)
Cline cannot read the terminal output terminal shell integration did not attach run the command in the terminal yourself and paste the output, or ask it to re-run
the assistant looks for mumps it did not read the contract put the contract where its section above says, start a new conversation
m: container 'm-devbox' is not running (host shim) the box is not up, or has another name start it as in the Claude Code steps; MDEVBOX_CONTAINER=<name> if you named it differently
m: … is not inside the project mounted at /work (host shim) you ran the assistant outside the mounted directory cd into the project you mounted
the key is rejected provider and key do not match, or the model is not on that key check the provider in Cline's settings (gear icon) or your CLI's login
it loops on a failing test guessing switch Cline to Plan (or tell the CLI to stop and explain); ask for the failure in one sentence before any edit
