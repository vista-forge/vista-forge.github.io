As the coordinator

Section titled “As the coordinator”

The same one-line change as above — the Lab Results alert, Disabled to Enabled, on vehu — made as a person. Captured 2026-09-21 against VSL*1.0*90.

Without a sign-on, v setup reaches a system over the driver, where nobody signs on and the engine's user is the seam's user 1. With --as (a declared identity, for demonstration systems) or --sign-on (asks for your access and verify codes on the terminal, echo off, never stored), every request of the verb rides the RPC Broker as the person Kernel signed on. That matters because the engine asks Kernel, before it writes, whether that person may run the VistA menu option they would otherwise have used for the setting.

The plan, as the coordinator

Section titled “The plan, as the coordinator”

ten is vehu's demonstration coordinator, VEHU,TEN — an ordinary clinician, not a programmer.

Three things are new on this plan. Allowed by option is the VistA option Kernel let him through — ORB3 PROCESSING FLAG, Enable/Disable Notifications, the option a coordinator uses for this at a terminal; the engine derives which option guards which setting from VistA itself. Also on file lists the other levels holding a value for the same setting: the package default, and six people with their own — counted, never named. The plan does not say which of them wins: the alert package decides that, and not by the parameter file's own order. plan is this plan's identity — the file's name and a hash of its bytes — which the engine files on every change record an apply of it leaves.

The same plan, as a programmer

Section titled “The same plan, as a programmer”

vero is vehu's other Broker identity: a programmer, who bypasses the Broker's own context checks.

Exit 4. Holding the programmer key exempts nobody: his menus do not reach the option that guards the setting, so Kernel says no and so does the plan. Which option that is comes from a reviewed table the library ships, not from a reading of VistA at run time; the refusal is Kernel's answer in Kernel's terms. The 31 rows that already hold what the file says are still unchanged — a request that would write nothing asks nobody's permission.

Who changed it

Section titled “Who changed it”

VistA's parameter file keeps no history. Every write this tool applies files a change record in VistA first, and confirms it after reading the change back.

These are this repo's own live check at work: it adds one scratch row as the coordinator, changes it, and takes it back, on every run — and each of those writes is a true change, so each leaves its record. A record made over the driver path reads (stated, not signed on) beside the name: there, nobody signed on, and the engine only had the caller's word for who it was. When is VistA's own date form (3260921.214533 is 21 September 2026, 21:45:33).

What it does not do

Section titled “What it does not do”

The access and verify codes are what CPRS falls back to inside VA; VA's normal sign-on is the PIV card, which no system here can prove. Nothing on this page says that sign-on works. On a system reached only as a Broker client, the check that the engine's library is the build this tool was generated from cannot be made, and every result says so.
