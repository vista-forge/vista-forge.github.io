The database, plainly

If you have used any database before, you already know most of what follows — it is just wearing unfamiliar clothes. This section hands you the translation, because every noun in the command reference comes from here, and the commands make very little sense until the shape does.

One enormous tree

Section titled “One enormous tree”

Most databases you have met are made of flat tables and are queried with a language that plans its own execution. VistA is neither.

Underneath everything, VistA is one gigantic persistent tree — a sparse, sorted, on-disk nested dictionary. In MUMPS (the language VistA is written in) these trees are called globals, and a global reference looks like this:

Those three values are real — patient 1 on vehu, whose stored .01, .02 and .03 you can read back through the API at 2.6 (2350407 is a FileMan internal date: year offset from 1700, so 1935-04-07). The exact piece positions are a per-field property recorded in the data dictionary as node;piece, which v db schema and v db export now carry per field as storageLocation (VSL*1.0*65) — so the layout above is the shape, and the byte map is a read away.

The shape is the point, though, and it has a consequence you will meet again in 8.14: several fields share one string, delimited by ^, with no escaping. A ^ inside a value does not get quoted — it becomes a new piece boundary, and the record silently means something different.

The closest thing in a modern stack is a persistent, ordered key-value store whose keys are tuples — think a giant SortedDict keyed by ("DPT", 1, 0) that survives restarts, or a filesystem where every directory can also hold a value. Three properties matter and are worth internalising before anything else:

  • Sorted. You can always ask "what is the next key after this one", which is the operation VistA is built out of. ($ORDER, in MUMPS.)
  • Sparse. A node exists only if something was stored there. There is no fixed row width and no NULL-padding; absence is the default.
  • Schema-less at the storage layer. The tree itself does not know that ^DPT(1,0) holds a name, a sex code and a birth date crammed into one string separated by ^ characters. Something else has to know that.

That "something else" is FileMan.

FileMan is VistA's database management system — the layer that gives the tree a schema, a type system, validation, indexes, and an API. It is the counterpart to a relational engine's catalog + query layer, except that it sits on top of storage that other code can also reach directly. Every VistA application is written against FileMan; the tree underneath is FileMan's business.

So: the tree is the disk; FileMan is the database.

The tree, drawn

Section titled “The tree, drawn”

Two pictures. The first is the whole database; the second is one record.

Every file lives in the same namespace. There are no separate databases, schemas or tablespaces — each file simply owns a subtree, and the subtree it owns is recorded in its data dictionary entry as the global root:

Note the two on the left. ^DD holds the schema — every field name, type, pointer target and index definition in the system — and ^DIC holds #1 FILE, the catalog of files, which is itself an ordinary file. VistA describes itself, in its own data model, in the same tree as the data. That is what lets a generic tool walk an instance it has never seen.

The diagram draws the five as siblings for clarity, but roots can nest: #1 FILE is at ^DIC( and #19 OPTION is at ^DIC(19, — so the OPTION file physically lives inside the catalog's own subtree. A global root is just an address, and nothing requires two files' addresses to be disjoint.

Now one record, exploded. This is #2 PATIENT on vehu:

Four things that picture is trying to tell you, in rising order of importance:

  1. A record is a subtree, not a row. It has no fixed width. Fields are packed several-to-a-node and read by position, which is why a ^ inside a value is not an escaping problem but a structural one — it creates a boundary that was not there (8.14).
  2. A sub-file is physically inside its parent. #2.01 ALIAS is a real file with its own fields and its own B index, but no global root — its rows hang off the record they belong to. There is no join because there was never a separation. On vehu, 671 patients have exactly one alias, 12 have two, and one has three.
  3. The two orders are different, and the picture shows it. Records sit in IEN order; the B index sits in name order. Its first two entries on vehu are ALPHATEST,NEW ONE → 100841 and ANOTHER,CLONE → 101042 — alphabetically first, numerically nowhere near the front. Walking the index and walking the file visit the same records in completely different sequences, which is why a cursor for one is not a cursor for the other. Gaps are normal too: #3.1's records run 1, 2, 3, 4, 5, 9 — never iterate 1..n.
  4. ⚠️ The index is a sibling of the data, not a view of it. "B" sits under the same root as records 1, 2 and 3 — but it is a separate structure, written by code that fires when a field changes. If that code did not run, ran twice, or was added after the data landed, the index and the records disagree. Nothing about reading the index reveals this.

That last point is the whole reason this domain exists, and the diagram makes it physical. The two things you can walk are not the same thing:

The legacy generic read path walks the second and reports it as though it were the first. v db walks whichever you asked for and stamps which one answered on every page — that is the population line you will see in every transcript from here on.

What is measured here, and what is drawn. Measured live on vehu today: the global roots and record counts of all five files above; that #2.01 ALIAS is a sub-file of #2 with an empty global root, three fields and a B cross-reference; the ALIAS depth distribution (671/12/1); IEN 1's stored .01, .02 and .03 values; and the first two B-index entries with the IENs they resolve to. Drawn as FileMan's standard layout, not measured: the exact node subscripts for the multiple and the index, and the piece positions within the 0 node. A field's real storage location is recorded in the data dictionary as node;piece, varies per field, and is surfaced per field as storageLocation (VSL*1.0*65) — so this drawing can be checked against v db schema 2.

The records room

Section titled “The records room”

FileMan was designed in the late 1970s for people who had spent their careers running a hospital medical-records room, and it shows — in a good way. The analogy is not a teaching aid bolted on afterwards; it is the actual design. Hold it in your head and almost every quirk becomes predictable.

in the records room in VistA in a modern database
a filing cabinet, with a number stencilled on it a file (#2) a table
a numbered folder in that cabinet a record, identified by its IEN a row, identified by its primary key
a pre-printed form inside the folder, with numbered lines the file's fields columns
line 1 of every form: the patient's name field .01 the natural-key / name column
a continuation sheet stapled inside the folder a multiple / sub-file a child table — but physically nested inside the parent
writing "see cabinet 11, folder 2" instead of copying the text a pointer a foreign key
the card catalogue by patient name at the front of the room a cross-reference (index) an index
the master list of what every cabinet contains the data dictionary (^DD) information_schema / the system catalog
the clerk who knows the forms, checks your handwriting, and refuses a bad date FileMan the DBMS

The room has one more property that turns out to be the crux of this whole guide: the card catalogue is not the cabinet. If a card was never filed, or was filed twice, the catalogue disagrees with the drawer — and looking things up through the catalogue will never tell you so. Hold on to that; it is 3.4.

Files

Section titled “Files”

A file is VistA's table. The first thing to know is the thing that surprises everyone:

Files are identified by number, not by name. #2 is the patient file. The number is the identity; the name is a label that could in principle change.

Those numbers are assigned nationally, so #2 is PATIENT at every VA site in the country. They are also hierarchical by convention — related files cluster in a numeric neighbourhood, and a sub-file's number extends its parent's (#2.025 lives under #2).

Read that line as: the table called PATIENT is table number 2, its rows live in the tree ^DPT(, it has 594 columns, and 379 other tables have a foreign key into it. A production VistA carries thousands of them: vehu's dictionary walk covers 8,262 files and sub-files, of which 2,919 are top-level entries listed in #1.

Four you will meet constantly:

file name tree records on vehu what it is
#1 FILE ^DIC( 2,919 the file of files — the catalog, itself a file
#2 PATIENT ^DPT( 1,755 the master patient record
#200 NEW PERSON ^VA(200, 1,496 every user, provider and staff member
#19 OPTION ^DIC(19, 13,198 the menu/option tree — VistA's application registry

#1 is worth a pause. VistA's catalog is not a special system view outside the data model; it is an ordinary FileMan file that you can read with the same verbs as any other. That self-description is why a generic tool like v db can exist at all.

Records and IENs

Section titled “Records and IENs”

A record's identity is its IEN — Internal Entry Number. It is the primary key, and it is what the tree is subscripted by: ^DPT(1,…) is patient 1.

Four things about IENs that will bite you if you assume otherwise:

  • They are per-file. IEN 2 in #11 and IEN 2 in #2 are unrelated. An IEN is only meaningful paired with its file number.
  • They are allocated ascending, but not densely. Deletions leave holes. Never assume 1..n:
  • They are not always integers. .5 is a real IEN in #200 (it is POSTMASTER). This is why v db get treats the IEN as a byte-exact string and not a number — .5 and 0.5 are different keys.
  • ⚠️ They are site-local and not portable. Patient 1 here is a different human from patient 1 at the next VA hospital. An IEN is a physical address within one instance, never an identifier you may carry across systems or store in an export. (The portable identity is the .01 value, or a genuine national identifier where one exists.)

Fields

Section titled “Fields”

Fields are numbered too, and like file numbers the number is the identity. Field numbers are decimals, they are not contiguous, and their order is historical rather than meaningful — #2 has fields .01, .02, .03, .05, .09 and 991.01.

Field .01 is special and always exists: it is the record's name — the natural key, the thing the default index is built on, and the value FileMan will show you when something points at this record. In the records-room analogy it is line 1 of the form.

Multiples and sub-files

Section titled “Multiples and sub-files”

Here is where VistA departs from the relational model for real.

When a patient can have several addresses, a relational schema gives you a second table with a foreign key back. FileMan instead lets a field contain a whole table. Such a field is a multiple, and the table it contains is a sub-file with its own file number:

A sub-file is a real file with real fields — and it knows its parent, and it has no global root of its own, because it does not live anywhere independently:

That empty globalRoot is the entire point: the child rows are physically inside the parent's subtree. There is no join to perform because there was never a separation. Sub-files nest arbitrarily deep — a multiple inside a multiple inside a multiple is ordinary VistA.

Because a sub-record's identity is the path to it, addressing one takes more than an IEN. That address is the IENS, written innermost-first and always comma-terminated:

IENS means
42, top-level record 42
1,42, sub-record 1, inside record 42
3,1,42, sub-sub-record 3, inside sub-record 1, inside record 42
+1, "a new record" — used when creating
+1,42, a new sub-record under record 42

You will pass IENS strings to v db edit, delete and text. The trailing comma is not decoration — an IENS without it is refused.

Pointers

Section titled “Pointers”

A pointer field is a foreign key: it stores the target record's IEN, and FileMan resolves it on the way out. #2's .05 MARITAL STATUS is P11' — points at file #11.

Two variants worth knowing:

  • Variable pointer (V) — a polymorphic foreign key: the field may point into any one of several files, and the stored value carries which. The modern analogue is a (type, id) pair collapsed into one column.
  • DINUM — a file whose records take the same IEN as the record they point at. It is the FileMan idiom for a strict 1:1 extension table: "row N of this file is by definition about patient N." v db schema reports it as dinum: true, and v db put refuses such files outright, because every way FileMan offers to create one was measured defective.

Pointers are also how you find a file's blast radius. pointerIn counts the files pointing at this one, and it is the number to look at before you touch anything:

1,244 files point at #200 NEW PERSON. That is what "load-bearing" means in VistA, and it is not something FileMan surfaces conveniently — which is why schema computes it.

Cross-references

Section titled “Cross-references”

A cross-reference is an index: a secondary tree, maintained as data changes, that maps a value to the IENs holding it. By near-universal convention the index on .01 is called B — so "the B index" means "the by-name index," on every file in VistA.

Indexes are what make lookup fast, and v db find walks one directly. But an index is a separate structure from the data, maintained by code that runs when a field changes — and code can fail to run, run twice, or have been added after the data. So an index can be incomplete, or can hold an entry twice, and nothing about reading it tells you which.

This is the records-room point again: the card catalogue is not the cabinet. It is the single most important thing to understand about VistA data access, it is the reason v db distinguishes find from rows, and it is the reason every read answer states which population it came from:

  • population index:B — this answer is the catalogue's.
  • population file — this answer is the drawer's, walked directly.

Globals and the data dictionary

Section titled “Globals and the data dictionary”

Two trees, side by side:

  • The data lives at the file's global root — ^DPT( for #2, ^VA(200, for #200. Within a record, values are packed into nodes as ^-separated pieces: ^DPT(1,0) holds name, sex, date of birth and more in one string. This is where the ^ character earns its reputation — a ^ inside a value would split the node and silently corrupt the record, which is why v db refuses one at the door (8.14).
  • The schema lives in ^DD — the data dictionary. Field names, types, pointer targets, input transforms, index definitions: all of it is data in a tree, readable at runtime. v db schema is a structured read of ^DD.

That the schema is itself queryable data is the property everything in this domain rests on. A generic tool can walk any VistA file on any instance without being told anything in advance, because the instance can be asked.

Where the analogy breaks

Section titled “Where the analogy breaks”

Every analogy has an edge, and running into these at speed is how people form wrong expectations about VistA. Four to hold on to:

  1. There is no query language and no planner. Nothing takes a declarative request and decides how to execute it. You choose the access path — walk the file, or walk a named index — and that choice is the plan. This is why v db makes you say rows or find, and why it reports which one answered.
  2. There are no joins. A pointer is resolved one record at a time, on demand. Nothing assembles a result set across files. If you need data from two files, you read two files.
  3. COUNT(*) is not free. There is no maintained row count. Every file header carries a number, but it is a claim that maintenance code updates — and it drifts. v db count walks the file to answer honestly, which is why it prints walked and claimed side by side, and why on #757.02 those differ by 167.
  4. The storage layer is reachable without the schema. Nothing physically stops code from reading and writing ^DPT( directly, bypassing every type, transform and index FileMan would have applied. Plenty of VistA code does. This is the deep reason a database "constraint" in VistA is a convention enforced by a layer, not an invariant enforced by storage.

None of this is criticism. It is a design from 1978 that has run a national health system for four decades, and its priorities — self-describing schema, data that outlives the code, no dependency on a commercial engine — were the right ones. But if you arrive expecting Postgres, you will misread what you see.
