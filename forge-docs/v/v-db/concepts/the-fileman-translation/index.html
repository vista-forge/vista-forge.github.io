The FileMan translation

With the vocabulary from section 2 in hand, the command surface stops looking like VistA and starts looking like a database CLI. Here is the whole thing against what you would reach for elsewhere.

v db roughly what it actually does
schema DESCRIBE / information_schema one file's columns, types, pointer targets, indexes, and who points at it
census table sizes across the database walked record counts for every file, with the header's claim beside each
export pg_dump --schema-only, to a file the whole dictionary as JSONL + a manifest — the extraction seam
refs information_schema.referential_constraints one file's foreign keys, both directions, with --verify auditing FileMan's own catalog
estimate capacity planning record count × sampled size over a file set, fitted to a cap
count SELECT COUNT(*) an honest count — walked, not read off a header
rows SELECT … LIMIT + a cursor (never OFFSET) one bounded page, walking the file itself
get SELECT … WHERE pk = ? one record by IEN
find an index seek / WHERE indexed_col LIKE 'x%' walks a named index, seeking rather than scanning
distribution GROUP BY col ORDER BY count(*) DESC value variety, or sub-file depth
fields-profile count(col) FROM t for every column at once which columns actually hold data here — one walk, not one per column
policy GRANT / REVOKE the declared per-file authorization surface
put INSERT create a record, validated whole-request
edit UPDATE file values into an existing record
delete DELETE remove a record — dry-run by default
reindex REINDEX rebuild one record's cross-references
text reading/writing a CLOB column the word-processing accessor

Five of those have no clean equivalent anywhere else, and they are the ones worth understanding before you start:

count exists because COUNT(*) does not. No engine maintains a row count here. The number in a file's header is a claim kept up to date by maintenance code, and it drifts — on vehu's #757.02 it is wrong by 167. So count walks the file and prints both numbers, and leaves you to notice.

find and rows are separate verbs because the access path is your decision. There is no planner to make it for you. rows walks the drawer; find walks the card catalogue. They can legitimately return different answers, and which one you used is stamped on every response as population.

distribution exists because FileMan has no API for variety at all. "How many distinct values does this field have, and how many records are empty" is a question you cannot ask the DBS, and it is usually the first question worth asking before building anything on a field.

text exists because word-processing fields have no write path. FileMan's validator refuses them, the FDA loader accepts them anyway, and DDR never calls WP^DIE. This verb is new construction, not a port — and its read face is something DDR never had.

estimate is the only verb here that is not a database read. It sizes a prospective extract — record count × sampled record size over a file set, fitted to a cap — because "will this slice fit" is a question somebody has to answer before any extract, and answering it by hand does not scale. It once had company: profile, list and diff classified every file into PIKS categories, and all three left this domain in 2026-08 along with the evaluator behind them (§7.7). v db surfaces the operational database as it is and adds no judgement of its own.

Why every read carries a completeness block. In a relational database you take for granted that SELECT returned everything matching, or told you it could not. Neither guarantee holds in the legacy VistA path — a lookup returns whatever its index contains, and a truncated result and a complete one look identical. So v db publishes, on every page, which population answered, how many candidates it visited, how many it rejected, how many it emitted, and which bound stopped it. That block is the guide's real subject, and it is section 7.1.

The whole surface, drawn

Section titled “The whole surface, drawn”

One picture, and the rest of this guide is detail. Every verb is drawn at the point in the tree it actually touches — which is the fastest way to see why there are eighteen of them and not one.

Read it in four passes:

  1. Top to bottom is the tree, in the order you would meet it: the schema (^DD), the catalog of what exists (^DIC), then the data itself.
  2. Left is structure, right is the verb that reads it. Every verb is at the depth it operates on — schema never descends past ^DD, get lands on one record, count never projects a field at all.
  3. The two arrows into the same file are the whole design. rows/count walk the numeric subscripts; find walks "B". Same file, different populations, and every response says which one it was. If you take one thing from this diagram, take that.
  4. Writes touch two places at once. A record's data and its index entries. That coupling is why put and delete are validated and transactional, and why reindex exists at all — when data and index disagree, something has to rebuild the second from the first.

Two things the picture deliberately leaves out, because they are the same for every verb: the transport (one bounded page per engine visit, over the m-driver-sdk seam — 1), and the completeness block that rides on every read answer (7.1). Node subscripts and piece positions are drawn as FileMan's standard layout, not measured — the caption at 2.2 says exactly which parts of this shape were measured on vehu and which are convention.

The FileMan translation table

Section titled “The FileMan translation table”

"I used to do this in FileMan. What do I type now?" — every load-bearing FileMan data-access surface, in plain English. Package-reach figures are measured counts of distinct calling packages on VEHU.

I want to… FileMan, as-is reach v db, to-be in modern terms
see a file's structure $$GET1^DID, FIELD^DID, FILE^DID 55 / 50 v db schema <file> DESCRIBE table
read one record's fields GETS^DIQ, $$GET1^DIQ 106 / 85 v db get <file> <ien> SELECT … WHERE pk = ?
list many records LIST^DIC 59 v db rows <file> SELECT … LIMIT + cursor
look something up by name $$FIND1^DIC, FIND^DIC, ^DIC, IX^DIC 89 / 73 / 135 v db find <file> <index> an index seek
count the records (read the header node) — v db count <file> SELECT COUNT(*)
count every file (no API) — v db census table sizes
see a field's value spread (no API — print-time stats only) — v db distribution <file> <field> GROUP BY … ORDER BY count DESC
see WHICH columns of a file hold data (no API — one report per field, or read the globals) — v db fields-profile <file> count(col) for every column at once
read a file's nested table (read ^DPT(n,m,…) by hand) — v db rows <sub-file>, or --with-multiples for the whole record as a tree a child table, or a nested document
read a named set of records (one GETS^DIQ per record) — v db rows <file> --iens 1,5,.5 WHERE pk IN (…)
see what the indexes actually store (hand-read ^DD(f,fld,1) and the #.11 INDEX file) — v db indexes <file> · --all SHOW INDEXES
know what a read will cost first (none — ^DIC picks an index and never says which) — v db rows/find … --explain EXPLAIN
map the foreign keys of the whole instance ^DD(f,0,"PT"), one file at a time, and it can be stale — v db refs --all --out DIR the whole FK graph as an artifact
add a record UPDATE^DIE, FILE^DICN 94 / 105 v db put <file> --value … INSERT
change a record FILE^DIE, classic ^DIE 96 / 126 v db edit <file> <iens> --value … UPDATE
delete a record ^DIK, FILE^DIE with @ 119 v db delete <file> <iens> DELETE (dry-run first)
check a value before filing VAL^DIE, VALS^DIE, CHK^DIE 23 / 5 (automatic — every write validates) mandatory CHECK constraints
enforce uniqueness $$KEYVAL^DIE, KEY file #.31 3 (automatic, inside the write) a unique constraint
write a long-text field WP^DIE, EN^DIWE 55 / 31 v db text … --line/--from-file writing a CLOB
read a long-text field (none — BROWSE^DDBR displays it) 14 v db text … --show reading a CLOB
rebuild an index IX1^DIK 48 v db reindex <file> <ien> REINDEX one row
control who may read/write $$CANDO^DIAC1, POLICY #1.6 1 v db policy --declare … GRANT / REVOKE
reach it from a remote client the ten DDR * RPCs 29 of 130 menus the VSL DATA PLANE RPC + its broker context option (7.8) a remote data API

Two rows are worth reading twice, because they are where the shape of the answer changes rather than its spelling:

  • "list many records" is not a rename. LIST^DIC answers from whichever index it traversed; v db rows answers from the file. On the 15 measured files those are different answers — and on #757.02 the legacy call returns zero rows for 855,565 records.
  • "check a value before filing" moved from a call you could forget to make into something you cannot skip. DDR VALIDATOR existed as an optional pre-check, which is precisely why writes went in unvalidated.

Where v db is a superset

Section titled “Where v db is a superset”

The honest answer, because a cheat sheet that implies coverage it does not have is worse than no cheat sheet.

v db is a superset of FileMan's record-grade data-access core, and is not a superset of FileMan. Those are different claims and the distinction is deliberate — it was ruled, surface by surface, in the effort's coverage map, which enumerated 26 FileMan access surfaces and dispositioned every one.

Superset — covered, plus capability FileMan never had:

the core status
DBS read (DIQ), DD read (DID), lookup (DIC), DBS + classic write (DIE), WP filing, validation, keys, delete, reindex ✅ covered by the verbs above
honest record counts ➕ new — FileMan has only a header claim
distinct-value / depth distribution ➕ new — FileMan has no aggregation API at all
per-field population profile (which columns hold data) ➕ new — there was no way to ask this at all; the nearest approach was one distribution per field
a completeness assertion on every read ➕ new — nothing in FileMan reports what its answer was drawn from
export sizing against a cap ➕ new — FileMan cannot tell you how big an extract would be
an instance-wide cross-reference inventory (indexes --all) ➕ new — FileMan has no listing of what its indexes store, in either register
an instance-wide pointer graph (refs --all) ➕ new — the pointed-to-by catalog is per file, and stale; nothing assembled or audited it
a plan before the read (--explain) ➕ new — FileMan chooses an index inside ^DIC and never says which, or what it will cost
a named record set as a population (--iens) ➕ new — a cohort was one GETS^DIQ per record
the stored entries of an index a seek refuses (find --raw) ➕ new — these are most of them, and they were reachable only by hand-walking the global

Not covered, on purpose — and where the capability lives instead:

FileMan surface why not here where it lives
print / report / templates (EN1^DIP, EN^DIS, PRINT #.4, SORT #.401) presentation, not data access your own tooling over rows/find output — but note v db has no sort-order control, which is a real limitation of rows
SQL projection (SQLI, Octo) a different query model no successor — the fm-explorer effort that owned this lane was retired 2026-09-07
bulk export/import (Extract, DDXP, Filegram, DIFROM, Import) measured near-dead (≤2 external callers each); bulk movement is a provisioning concern engine-native dump/load
merge / renumber (DIT, EN^XDRMERG) cross-record identity resolution, a genuinely harder problem never a v db verb
archiving (DIAR) operations; 0 external callers not addressed
ScreenMan / browser (^DDS, BROWSE^DDBR) UI the data underneath is reached by get / text
Entity / DDE (GET^DDE) FileMan's own JSON projection — but needs a pre-defined mapping per shape, so it is not general declined as prior art
audit-trail reading (^DIA, ^DDA) keeps one owner for the audit plane the vista-observability effort
direct global access this is the thing v db is the alternative to —

Genuine gaps inside the intended scope — open, not ruled out:

gap status
sub-file enumeration and projection CLOSED 2026-08-13 (VD-D31/VD-D54 discharged). It was the largest in-scope gap: rows 2.01 refused, and projecting a non-word-processing multiple refused with "insufficient information to identify an entry in a subfile". Both now work. rows <sub-file> walks a direct sub-file file-wide (population: sub:2.01, no parent needed), and --with-multiples projects every non-WP multiple inline and recursively into the record — the decoded tree in one invocation. Depth is no longer a limit either — #63.041, three levels down, walks file-wide on both engines. What remains is narrow and typed: a parent chain that does not resolve (over 20 levels or a dictionary cycle) refuses U-VSL-ROW-SUBFILE, and a record whose subtree outgrows the bytes budget comes back as a typed stub naming the paged alternative (U-VSL-ROW-TREESIZE) rather than a truncated tree.
whole-file reindex deliberately not a verb — but that means a full index rebuild still needs IXALL^DIK by other means.
creating or altering files and fields no verb. v db schema reads the dictionary; nothing in v db writes it. Schema changes remain a KIDS/FileMan job.
sort order on reads There is no ORDER BY, and a host-side --sort is refused on purpose: it could only sort the page it holds, producing a page-local ordering that looks global. What you get instead is order as a property of the population you chose, derivable from the population field every read already carries and stated in §11.5 — find <file> B is ordering by B's key, and --explain says which index gives which order.
batch atomicity single-record atomicity is proven and claimed; multi-record transactions are not offered.

If you are migrating a workflow off FileMan and it depends on a row in the second or third table, v db is not yet a drop-in for it — and this guide would rather say so than let you discover it halfway through.

Which gaps will stop you

Section titled “Which gaps will stop you”

Enumerating gaps is not the same as saying which ones bite. Ranked against the three things people actually come to a database tool to do:

# gap stops you at why
1 audit-trail content auditing — hard stop There is no v db path to "who changed this field, when, from what." Ruled to vista-observability (VD-D39), which is still a draft — so the capability FileMan has today has no tool at all. See below; the picture is more nuanced than "unimplemented".
2 no multi-field grouping, no joins, no ORDER BY reporting — moderately distribution groups one field only. Nothing assembles across files in one invocation: what you get instead is the guided client loop — --explain says what a read will cost, --ids says where to go next, --iens fetches the set in one conversation, and refs --all plus an offline closure (§9.1) says which files you need at all. Ordering is a property of the population, not a clause (§11.5).
3 what points AT one record reporting — narrowly refs --all answers it completely at file level. Per record it needs an index on the pointing field, which VistA usually does not have — measured, 8.7 % (§14.1).
4 no DD editing; no whole-file reindex management Schema changes stay a KIDS/FileMan job; a full index rebuild has no verb (only per-record reindex).
5 no batch atomicity management Single-record atomicity is proven; bulk corrections have no transaction.

Two entries left this ranking rather than being fixed in place, and both are worth knowing about. The RPC face was gap #6 until 2026-08-09, when VSL*1.0*39 installed the context option through a real KIDS post-install and the full acceptance matrix passed on both engines (7.8). Sub-files were gap #2 — "cannot page or project; multiples are where the interesting data lives" — until 2026-08-13, when the file-wide sub-file walk and --with-multiples landed (§8.8). Both are struck from the list on evidence, not optimism.

On metadata specifically — you are ahead, not behind. schema, refs, census, export and distribution give you more than FileMan ever offered: inbound pointer maps with an audit of FileMan's own catalog, honest record counts, a dictionary you can take off the engine, and value distributions FileMan has no API for at all. The gaps above are about data and audit content, not about the dictionary.

The audit picture, measured. It is worth being precise, because "no audit read" understates one part and overstates another:

  • ✅ You can see that auditing is configured. v db schema 2 reports audit: true per field — 101 of #2's 594 fields are audited.
  • ✅ You can see how much audit data exists. v db census --file 1.1 on foia: 43 records, ~358 MiB estimated — and the file header claims 0, so the walked count is the only honest one. #.6 DD AUDIT walks 36 (vehu: 0 — its audit machinery ships off).
  • ⚠️ The top level of #1.1 reads, but does not mean what it says. Its records are keyed by audited file number (3.5 → DEVICE AUDIT), while the DD's field set describes an audit entry — so .02 DATE/TIME RECORDED renders as 1701.1@1I:00. Plausible-looking output, wrong level.
  • ⛔ Two computed fields fault untyped. --fields 1 or 2.9 on #1.1 returns bare M6 / verb rows^VSLROW faulted, which also breaks --fields '*'. Computed projection works fine elsewhere (#200's 9001 and 2.2 both return values), so this is specific to this file — and an untyped fault is a contract violation regardless.
  • ⛔ The change records themselves are out of reach, because they hang below the top level — which makes this gap #2 wearing a different hat.

That last point is the interesting one: fix sub-file enumeration and most of the audit gap closes through the ordinary verbs, with no bespoke audit surface required. That reframing is under review in the effort's audit-read re-examination, and the whole gap-and-defect register — measured across both engines with a committed harness — is the gap remediation proposal. Two findings there change what is written above: only 37.5% of cross-references are walkable by find, and v db schema currently reports every cross-reference as regular, which contradicts it.
