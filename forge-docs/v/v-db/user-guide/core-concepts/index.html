Core concepts

The completeness block

Section titled “The completeness block”

Every read response carries it. There is no flag to turn it off, because a caller who does not ask for it is exactly the caller who gets silently wrong answers.

field meaning
population file (IEN walk) or index:<name> — the answer set's definition, stated rather than assumed
examined candidates visited
filtered candidates rejected by a predicate
emitted rows in this page
distinct distinct IENs in this page
stopped end | rows | bytes | examined | elapsed

stopped paired with more is what makes silent truncation structurally impossible. A page that ended because it hit a budget is distinguishable from a page that ended because the data did:

  • more: true, stopped: rows — your page size ended it; ask for the next page.
  • more: true, stopped: examined — a work budget ended it. If filtered is large and emitted small, you are paying for a scan.
  • more: false, stopped: end — the walk is complete. This is the only combination that means "that was all of it".

Duplicates. An IEN-ordered enumeration is distinct by construction. An index walk is not, and cannot be made so by a stateless cursor — so index walks report emitted and distinct separately and never silently de-duplicate. If find shows emitted 400, distinct 397, three records were emitted twice. Silently de-duplicating would replace a visible over-report with an invisible one.

Four bounds, and stopped

Section titled “Four bounds, and stopped”

Every paged read carries four bounds, each with a default, each overridable, each reported in stopped when it is the one that ended the page:

flag bounds why it exists
--max emitted rows the conventional one — insufficient alone
--bytes page payload bytes cost tracks field count, not row count; and the engine's own string ceiling
--examined candidates visited the one DDR lacks — the 34× scan is bounded by nothing else
--elapsed engine time in this page (ms) the backstop for what cannot be counted, since the DD permits arbitrary M in a computed field

--examined is charged for every candidate the verb touches, including a projection performed solely to evaluate a filter. That is deliberate: a filter on a non-indexed field must project that field per candidate, and a budget that charged only emitted rows would let a selective filter run an unbounded scan while reporting a small, tidy page — DDR's central defect, rebuilt.

--elapsed 0 is legal and means stop after the first candidate — useful for probing cost, and a compact demonstration that stopped really does name the bound that fired:

Cursors and resumption

Section titled “Cursors and resumption”

Paged verbs return an opaque page.next token. Pass it back verbatim as --token:

(Note IEN 9 following 5 — the walk is over the file's actual subscripts, gaps and all, not over 1..n.)

The token is opaque to you and carries a total order — (ien) for an enumeration, (key, ien) for an index walk — plus a binding fingerprint over file, population, field list and predicate. Replay it against a different request shape and you get a typed refusal rather than wrong rows:

The fingerprint covers the DD as well as the request, so a token also stops being valid if the file's dictionary changed underneath it. A non-advancing token raises PAGE_STALL instead of looping forever.

What is not offered, stated plainly: no snapshot isolation. Nothing on either engine provides it cheaply, and claiming it would be the same class of lie this domain exists to remove. The IEN walk's actual guarantee is precise:

  • a record present throughout the walk, at an IEN above the cursor's start, is emitted exactly once;
  • a record deleted before the walk reaches it is not emitted;
  • a record created during the walk is emitted if its IEN sorts above the current cursor — which, since FileMan allocates IENs ascending, is the normal case.

That is a bias toward including late arrivals, not a loss.

Projection: fields and tiers

Section titled “Projection: fields and tiers”

--fields takes ;-separated field numbers, or * for all:

Omit --fields and you get all top-level fields — which on #200 is well over a hundred. Name what you need.

"All top-level fields" has one measured carve-out: FileMan's retriever omits non-word-processing multiples from a '*' projection (on #200, 29 of 203 fields). The envelope now declares that instead of leaving it silent: every star page (and star get) carries a projection block naming each excluded field and why —

— so star ≡ the data dictionary minus the declared exclusions, checkably. An explicit field list never carries the block (you named the fields; nothing is omitted), and a WP multiple projects as a line array, so it is never in the list. Every read also carries completeness — including get (a minimal single-record block) and text --show (its total mapped into the same shape), so the "every read" contract holds verb-by-verb, not just where paging happens to run.

--tier selects the value form, and takes external, internal or raw. Which tier you pick decides whether your parser travels to another site — every result says so in its portability block (7.9). The engine default is external — FileMan's own retriever, so pointers resolve, sets decode, computed fields evaluate and formatting is FileMan's business rather than yours.

The difference is not cosmetic. #200's field 9.3 is a pointer:

Note the asymmetry with filters: projection is external by default, predicates run on the internal value (11.7). So on that field --where '9.3 = 9' matches and --where '9.3 = C-VT100' does not, while the row you get back says C-VT100. On a free-text field the two forms coincide; on a pointer, a date or a set-of-codes they do not.

Word-processing fields are emitted as line arrays, never ^-pieced: 196 of 45,295 OPTION description lines carry a literal ^, and any consumer that re-splits them corrupts them. Read them with v db text --show.

The raw tier's shape is nodes, not fields. --tier raw returns the record's data nodes by subtree walk — clone-grade, below field semantics. On get the row is data.row.nodes (plus data.row.value when the record root itself holds a value); on rows each row is data.rows[n].nodes. Keys are the subscript path below the record, comma-joined; each value follows the standard value contract (a JSON string, or {"b64":…} when the bytes are frame-unsafe). Because nodes are not fields, --fields cannot combine with --tier raw — the combination refuses typed U-VSL-ROW-RAWFIELDS. (It used to be accepted and silently ignored: the same 338 nodes came back on #200 with or without the flag. An accepted flag that does nothing is a lie; now it is a refusal.)

Two more field-door refusals worth knowing. Explicitly projecting a non-word-processing multiple (say #19's field 3.91) refuses typed U-VSL-ROW-MULTIPLE — sub-records are rows, not a scalar, and the sub-file read plane that will serve them is a later milestone. Whether a multiple projects is now predictable from schema: its wordProcessing flag carries the sub-file's own .01 word-processing fact, which is the measured discriminator (214 observations, zero breaks). And two files — #1.1 and #.6 — refuse every top-level read typed U-VSL-ROW-NESTEDROOT: their top-level IENs are file numbers (audit content nests one level down), so a top-level render would return wrong-level values under ok:true.

Waiting on the run-lock

Section titled “Waiting on the run-lock”

The driver stack holds one run-lock per engine, so two v db invocations against the same engine serialize. That is deliberate — it is what keeps a long fold from interleaving with a write. --lock-wait sets how long to wait before refusing:

It is a typed refusal, not a crash — exit 4, with a code you can switch on:

--lock-wait 0 means try once and give up. A stale lock (the holder is gone) is reported on stderr as a notice and the verb proceeds.

Which verbs hold it for a long time is worth knowing before you start one. The whole-instance sweeps hold it for their full run — measured on vehu (v0.7.1-4-gec3abcf, 2026-08-17), each verb over the entire dictionary:

verb wall clock records
export 15m36s 8,171 tables
refs 15m19s 19,187 edges
census 3m20s 2,920 files
indexes --all 4s 9,740 indexes

export and refs are the two that cost a fold; census is minutes; nothing else in the domain holds the lock for more than a moment. A single-file invocation of any of them is a moment too — it is the --all/whole-instance scope that sweeps.

Authorization and the mutates gate

Section titled “Authorization and the mutates gate”

Two layers, and the gate is engine-side at every verb's door — never a host flag you could bypass by editing the client:

  1. A declared per-file policy, evaluated engine-side, default-deny for writes. Show it with v db policy.
  2. The instance class. class=demo versus class=real, beside a live reading of Kernel's own PROD tripwire. The write verbs refuse to run against an instance holding real patient data until a real principal exists — refusing loudly rather than degrading quietly.

On top of that, every mutation needs --yes, which is refused both client-side and engine-side without it, and every engine-reaching mutation writes exactly one audit line.

Be honest about what this is, per transport: the CLI/driver seam runs every request as DUZ=1 with host-asserted attribution — it defends against operator accident, not against a malicious host, and that bound is the driver seam's permanently (Shape B, ruled 2026-08-09). The broker face (7.8) carries a real Kernel principal: the declared per-file policy is bypassed for a real, active, signed-on user (their RPC access was already gated by the context option, and mutations audit under their real DUZ), while the driver seam keeps its declared bound and its real-data write refusal forever.

Classification is elsewhere

Section titled “Classification is elsewhere”

v db used to classify every file and field into PIKS categories (patient / institution / knowledge / system) from a registry of hand-written heuristics, with list, profile and diff as its faces. That history is stated plainly rather than erased — the tool really did carry it.

All of it was REMOVED in 2026-08 — a ~3,860-line evaluator, its registry corpus, and its verbs — and the whole PIKS line was RETIRED 2026-08-17.

The reason is worth understanding, because it is the line this whole tool is drawn along. A PIKS label is a purely analytical derivative of v db's own extraction output: an inference computed on top of the export, never a measurement the tool makes. Nothing in the database says whether a file is "patient data" — that is a judgement, and no stored value can check it. v db surfaces the operational database as it is; anything derived by inference from that surface is downstream work by construction. A national-dictionary label join survived here until 2026-08-13 and went for the same reason plus one more: that dictionary is incomplete and untrusted, and an untrusted source must not be joined into an artifact whose charter is that every cell is a fact or a named non-fact.

Classification now happens downstream, in the bundle analysis, derived from the dictionary export this tool produces — one repeatable artifact, re-derivable by rerunning the export. Nothing is inferred inside v db.

What this means for you: the catalog and the dictionary export carry measurements, never judgements. If you want files labelled, derive the labels downstream from the export, at whatever trust level you can defend. See §15.

Reaching it over the broker

Section titled “Reaching it over the broker”

Since VSL*1.0*39 (M9, 2026-08-09) the data plane is reachable from a VistA RPC Broker client — the transport CPRS-class applications already speak — with the same engine-side contract as every CLI verb. This section is for application builders; nothing here changes the CLI.

What ships. The KIDS build registers one RPC, VSL DATA PLANE (RPC^VSLRPC, return type 2 = local array), and one type-B broker context option, also named VSL DATA PLANE, whose #19.05 multiple authorizes the RPC. The context's RPC list is filed by a real KIDS post-install (EN^VSLRPCI) — measured fact: it cannot ship as KRN component data (the filer installs a lying header) — so a fresh install works with no manual wiring.

The call shape. One request parameter, one chunked response:

  1. Sign on (XUS SIGNON SETUP → XUS AV CODE) — the session now carries a real DUZ.
  2. XWB CREATE CONTEXT with VSL DATA PLANE. Kernel's own option-access check ($$CHK^XQCS) gates this: the signed-on user must hold the option (menu tree or secondary menu) or the XUPROGMODE key, else the broker refuses with "does not have access to option VSL DATA PLANE" — that refusal is the authorization model, exercised live in the acceptance.
  3. Fire VSL DATA PLANE with one literal parameter: the base64-encoded JSON request — the same json^VSLAPI contract the dispatcher speaks ({"verb":"rows^VSLROW","params":{…},"page":{…},"envelope":2}; mutating verbs add "confirm":1, "attrib":{"osUser":…,"host":…} and optionally an "idem" token).
  4. The response arrives as CRLF-delimited type-2 array chunks; concatenate them and you hold the framed VSL envelope (##VSL2:<n>##…##VSLEND##), byte-identical to what $$run^VSLAPI returns on the driver seam — measured raw-equal on both engines (803 B vehu / 783 B foia) at acceptance. Completeness block, typed errors, cursors: all identical.

What the real principal changes. Mutations audit under the signed-on DUZ (not the driver seam's asserted attribution); the declared per-file policy is delegated past for a real, active principal; and production-class writes are broker-only by design (VD-D48). Idempotency tokens and the typed U-VSL-ROW-LOCKTIMEOUT contention refusal work over this transport exactly as engine-side — a replayed token returns {"replayed":true,…} without re-filing or re-auditing, and a concurrent duplicate either serializes to a replay or refuses typed U-VSL-API-IDEMBUSY.

Concurrency is different here — plan for it. There is no run-lock on the broker path: sessions run in genuine parallel (measured ~6.2× effective parallelism at 8 sessions on vehu, graceful under composed load). Two rules from the acceptance:

  • Your read timeout must exceed the fired verb's worst case. A client that gives up mid-RPC abandons its broker job, which can spin at 100% CPU engine-side until reaped — measured live. Budget the timeout from the verb's bounds (elapsed defaults to 10 s/page), not from optimism.
  • On IRIS Community instances, respect the licence pool (foia: 8 connections, ~4 free after boot) — each broker session holds a slot for its lifetime.

Instance provisioning notes (operator, not client, concerns): broker signon needs per-instance credentials and — a measured gotcha — the XWB cipher table (XUSRB1) differs between instances (vehu's and foia's do not match); the org keeps foia's extracted table beside auth.env. Details: the acceptance record and docs/memory/engine-auth-env-wiring.md.

The full evidence for everything above: m9-acceptance.md.

Which instance answered

Section titled “Which instance answered”

Every result v db produces — every read, every write, and every refusal — carries two blocks that answer questions you would otherwise have to discover the hard way.

instance — which VistA answered. --engine vehu is a name on your machine, not an identity; the station number is what everything downstream partitions on. Hold two result sets from two sites and this is the only field that tells them apart. It is an opaque string: foia's is "050", and a numeric coercion anywhere downstream silently merges it with "50".

Three states, and they are three different facts:

state means
ok the engine read its own identity
unreadable the engine looked and could not — error says why (a bare engine with no Kernel says exactly this)
undeclared the engine predates VSL*1.0*52 and was never asked

undeclared is not unreadable. An engine that was never asked has not reported an absence, and rendering the two the same way would tell you this site has no station when in truth nobody looked.

portability — whether this tier's rendering survives a change of site. This is the property the rest of this section exists to warn you about, stated in the envelope instead of left to be met as a bug.

contract means
portable the rendering was measured to be the same across instances
instance-specific it was measured to differ — a parser written against this site may not span another
unmeasured no claim either way (this is what raw gets — it was not in the comparison)

portableTier names the tier that is portable, so a caller reading an instance-specific rendering is told where to go rather than only that it has a problem.

Why external is instance-specific. Two live instances, every populated file, every field, both tiers: on the subset where the comparison carries weight and the rendering is FileMan's rather than the data's, the external tier had 180 subjects whose value shapes did not intersect and the internal tier had 1. Dates are the axis. The two instances hold different records, so the comparison is of the grammar, not of a value: #200's field 2.2 renders JUN 10,2010 on vehu and APR 20, 2026 on foia — same field, and the difference that survives every change of data is the space after the comma. Every external date rendered in FileMan's MMM DD, YYYY grammar differed between the two instances that way. It is a substrate property, not a v db defect: both renderings are legitimate FileMan externals, so no single consumer parser spans both instances.

And it is not reachable by filtering on type — #200 field 2.2 is computed, #776 field 9 is a pointer, and both carry the same divergence. Hardening "your date fields" does not cover it. Ask for --tier internal.

scope travels with the claim, deliberately. It reads "2 instances at FileMan 22.2" because that is what was measured — both class=demo. A bare "internal is portable" would read as a fleet-wide guarantee, and this is not one. Measurement: P3 closure.

What is NOT claimed. That two instances hold the same values — they do not. That free text agrees — it does not, and it diverges identically on both tiers, because there is no rendering for a tier to change. That a third FileMan flavor behaves like these two.

The same property bites find's key bounds. --from, --to and --prefix operate on the stored, collated key space (8.10), and what is stored is site data: the same command can return different boundaries on two sites, and a prefix that selects a page here may select nothing there. That is not an inconsistency to file — it is the same "the rendering is the site's" fact, one layer down, and the instance block on the result is what lets you say which site the boundary came from.

On the text face both blocks print as one line each, after the command's own output:

Refusals declare too, which is when it matters most: two instances answering the same command differently is exactly when one of them says no.

How you know a read is true

Section titled “How you know a read is true”

Every other section of this chapter is about what a read says. This one is about why you should believe it — and it exists because on 2026-08-18 the tool was, briefly, wrong in the worst possible way: 32 export passes exited 0, every one reported complete: true, every stream matched its own sha256, and the payload was 8.6 MB lighter than the day before, with field descriptions gone from 7,166 of 8,170 tables. Nothing caught it. It was found by eye, three screens deep in a viewer, because one header count looked low.

The lesson that produced everything below is one sentence: a digest computed by the writer attests what the writer saw, not what the database holds. Four distinct guarantees now sit between the stored global and the bytes you parse, and they are worth knowing apart, because a consumer usually needs all four and they fail in different ways.

1. The engine is running the code this host was built against. Before its first dispatch, v db folds the installed source of every engine routine it will call — 62 of them — and compares against a table generated from the pinned manifest. A mismatch refuses, SOURCE_DRIFT or SOURCE_PIN, naming the routine and both folds. This is exact source identity, not a version string, so a hand-patched routine or an unregistered load is caught even when the version it reports is right.

This refusal is common and it is not a bug. Every engine ship trips it on every deployed consumer until that consumer's pin is regenerated. It names four suspects — the engine, the committed pin table, the composed module pin, and the built binary — and the last is gitignored, so a repo that is completely current in git can still refuse every read. Check the binary's age before you go looking for a broken engine.

2. The envelope arrived intact. The engine stamps every successful envelope as it is framed; the host recomputes on arrival and raises INTEGRITY_FAIL / INTEGRITY_MISSING if they disagree. That covers the truncation, escaping and transport band, on every page of every verb, for about a quarter-second per megabyte of payload.

3. What the read returns matches what the global holds. This one cannot be checked by the read itself — two readings that share a code path are one oracle presented as two, which is precisely why the dictionary fingerprint was byte-identical across the regression above. It is checked instead by instruments that do not share the path: a three-way join of the interpreted value against the storage location the dictionary declares against the bytes actually at that position; the same for the dictionary plane through two independent channels; and an out-of-band engine-native dump that uses no driver, no envelope and no JSON encoder at all. They are not part of make check — they need live engines — and they run per release. Detail: technical reference §2.11.

4. The database itself is self-consistent. That is a different question again, and it has its own verb: integrity is a census of the instance's own damage — dangling pointers, hollow records, nonconforming values, key violations, index divergence — every class reported against its own denominator. It is worth internalising that a healthy VistA is not clean in any of those classes: a stock release build ships with nonzero counts, so an absolute number means nothing until it is compared against a baseline (integrity-compare).

What to take from this if you are consuming an artifact. Its sha256 says the file matches what the writer wrote. Guarantees 1 and 2 say the writer was talking to the engine it names, through verified code, over a transport that did not corrupt anything. Guarantee 3 says the read matched storage when the instruments last ran. Guarantee 4 says what was already wrong inside the data before anybody exported it. They are four different claims and an artifact's digest is only the first one — which is the whole reason the manifest carries the instance identity, the request, the completeness block and the engine build alongside the hash.
