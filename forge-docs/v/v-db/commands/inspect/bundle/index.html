v db bundle
Group Inspect
Engine access read
Mutates data no
Reversibility not applicable (does not mutate)
Exit classes 1 (runtime error) · 2 (usage error) · 3 (check / gate failed)

Synopsis

Section titled “Synopsis”

Arguments

Section titled “Arguments”
Argument Type Required Description
set string yes The run set: a TOML file naming the components this bundle is made of, each a verb plus its arguments (sets/dd-bundle.toml is the committed one).

Flags

Section titled “Flags”
Flag Type Default Env Description
--engine string vehu V_ENGINE VistA engine profile to reach (vehu = YDB, foia = IRIS, local = in-image YDB).
--lock-wait duration 30s — How long to wait for the engine run-lock before refusing (0 = skip immediately when busy).
--timeout DURATION duration — — Host wall-clock bound on ONE engine visit; a hung page is aborted engine-side, not just abandoned. Unset = the verb's derived default (180s; a whole-instance sweep verb pins a slower one); negative = no bound (still reapable by hand).
--out string — — Write the bundle here: one directory per component, each with its own manifest, plus bundle.json and a byte-identical copy of the set that produced it.
--group NAME list (separator ,) — — Run only the components in these groups (repeatable). Every component left out is named in the bundle record with the reason. Without it the whole set runs.
--explain bool — — Report what this set WOULD export and exit, without reaching an engine or writing anything: every component, its group, its purpose, its verb and its resolved arguments — and, if the set has problems, all of them rather than the first.
--base DIR string — — A previous bundle directory to certify drift against, always NAMED — never a baseline the run finds for itself. Record and byte drops are reported; a per-key density collapse (a key that carried values there and carries none here) refuses the run at that component. Without it drift is recorded as unmeasured.

Example

Section titled “Example”

A json artifact, contract version 1.0.

  • bundle.json
  • set.toml

Typed refusals

  • BAD_BASE
  • BAD_EXPLAIN

Notes

Section titled “Notes”

Hand-written in the owning repository; the facts above are generated.

A bundle is the whole picture of one instance's dictionary and its behaviour, interoperability and UI-join planes: a directory holding one artifact per component, each with its own manifest. Until 2026-08-23 it was produced by a shell script carrying 32 hand-written invocations — adding a plane meant editing bash in four places, and the answer to "what is in this bundle?" was to read that bash.

bundle runs a run set instead: a committed TOML file naming each component, its group, and a sentence saying why it is in the bundle. sets/dd-bundle.toml is the committed one.

Ask what it exports first

Section titled “Ask what it exports first”

--explain reaches no engine and writes nothing. It is worth running first for a reason that is not politeness: every component is resolved against the tool's own generated command contract before any engine work begins. An unknown verb, an unknown flag, or a flag that belongs to a different verb refuses here — so a typo costs a second instead of thirty-seven minutes. All the problems are reported, not the first, because a set is edited by hand.

Run it

Section titled “Run it”

Each component lands in its own directory under --out, with its own manifest.json — the same artifact each verb writes on its own. Beside them the run writes bundle.json (the record) and set.toml (the set that produced it, byte-identical and digested).

Four things about a run are worth knowing before you start one:

  • The whole set holds the engine for the sum of its components. On vehu the export alone is about a quarter of an hour. A busy run-lock is therefore probed and refused before the first sweep, not forty minutes into one.
  • A failing component STOPS the run at that component. Nothing after it is dispatched; bundle.json names where it stopped, which check fired, and every component that never ran (stopped), and each component already on disk is marked refused (below). A producer that cannot vouch for one component must not keep industrialising more of them.
  • What is not run is named with its reason — the components a --group run left out, and the components the set itself declares it does not carry. An absence you can read is a fact; an absence you have to notice is not.
  • A number that was not measured is absent, never zero. A component that wrote nothing reports records: unmeasured.

Every component is certified as it lands

Section titled “Every component is certified as it lands”

Immediately after a component is written — never as a final sweep — the run re-reads it and certifies five layers, in order, stopping at the first red. The re-read shares nothing with the writer: its own file handle, its own hash, its own line count, so the writer's claims are checked by a second oracle rather than repeated by the first.

layer what it checks what it catches
integrity independent re-read and re-hash; line count against records; every line parses truncation, a partial flush, a hash over something other than what landed
shape every record's keys against the schema generated from the tool's own serialising types, shipped in the bundle as schema.json a key silently added, renamed or dropped by a producer change
completeness the manifest's complete claim re-derived, and the per-page evidence's own arithmetic a page that stopped early and said so in a field nobody read
density per key, how many records carry a non-empty value — counts over denominators, recorded in certification.json keys intact, values gone — the failure that actually happened on 2026-08-18
drift records, bytes and per-key density against a named previous bundle (--base) a change that impoverishes the payload without breaking anything

The results land beside each component as certification.json (the full five-layer record, density included) and in bundle.json as each pass's certification verdict. schema.json states, per stream, whether its schema was reflected from the serialising Go types or declared (the rows envelope, whose records are rendered engine-side) — the two carry different guarantees, and the consumer is entitled to know which it holds.

Drift compares only against a base you name. --base <dir> points at a previous bundle directory; record and byte drops are reported loudly, and a density collapse — a key that carried values there and carries none here — refuses the run at that component. Without --base, drift is recorded as unmeasured; the run never goes looking for "the last bundle" on its own.

When certification refuses, everything already written is marked. Each component directory the run produced — the failing one included — receives a refused.json naming the component that stopped the run and the check that fired. The artifacts stay on disk for diagnosis, but each one says out loud that its bundle refused; a partial bundle must never read as a smaller whole one. A later green run into the same --out re-certifies and clears the marks.

It checks itself both ways

Section titled “It checks itself both ways”

bundle.json carries a reconciliation block, and it is published whether or not it found anything: an empty finding list is a measurement, and omitting it would make a clean run indistinguishable from one that never looked.

finding what it means
missing a component the set declared landed no complete artifact
unasked a directory in the bundle no component asked for — a leftover from an earlier, larger set, which otherwise reads as part of this one
instances the distinct instances the components measured. More than one is a bundle assembled from two places, which nothing downstream can untangle

Any of them, on a run that reached its end, exits 3 with BUNDLE_INCOMPLETE. A run that stopped — a component failed, or its certification refused — exits 3 with COMPONENT_REFUSED instead, naming the component and the check that fired.

Selecting one plane

Section titled “Selecting one plane”

--group is repeatable. A group no component carries is refused rather than run: it would otherwise select nothing and report a clean, complete, empty bundle.

What a set may not say

Section titled “What a set may not say”

A component names what to export. These flags belong to the run and are refused inside a component — --out, --engine, --lock-wait, --timeout — because a set that pinned them would work against exactly one instance with one set of bounds, and the point of a set is that it works against any. Refused too: a verb that can change the instance (a bundle is an export), a verb that lands no artifact (there would be nothing to reconcile), and bundle itself (a set that runs itself has no bound).

Measured properties

Section titled “Measured properties”

The run-set orchestrator (VD-D94/D95/D96). A run set is a committed TOML declaration of the components a bundle is made of — each a verb plus its argv, with a group and a sentence saying why it is in the bundle. sets/dd-bundle.toml is the committed one; its groups are structure, attribution, behavior, interop and ui-join, and the set itself is the denominator — bundle --explain prints the components rather than restating their count here.

Resolution precedes every engine visit. Each component is resolved against this binary's OWN generated command contract — reflected from the live kong tree, not read from a committed file that could be older than the code running. Refused at resolve time, all problems at once rather than the first: an unknown verb; an unknown flag; a flag belonging to a different verb (the case the ruling was written for — a flat list of every known flag would pass it); a run-owned flag (--out, --engine, --lock-wait, --timeout); a verb whose declared engine class is write; a verb with no --out; a component naming bundle itself; a duplicate component name; a declared exclusion with no reason. The set is parsed strictly: a key this format does not know is named and refused, because a key read past is an operator's written intent silently dropped.

Dispatch is IN PROCESS, re-entering this domain's own grammar with the resolved argv. Nothing is shelled out: a subprocess would have to know whether it is the standalone v-db binary or the v umbrella that mounts this domain as v db, and would get it wrong on one of them. Each component's own JSON envelope rides its own <name>.log; the run's verdict is the only thing on stdout.

What lands. One directory per component, each carrying the artifact and manifest that verb writes on its own — bundle recomputes none of those numbers, because the artifact is the authority on itself. Beside them:

file what it is
bundle.json the run record: per component its argv, exit, duration, projection tier, both digests, the manifest's own records/bytes/complete, and its declared instance; plus the set identity, what was not run, what failed, and the reconciliation
set.toml the set that produced the bundle, byte-identical and digested (VD-D94) — a bundle read a year later cannot be checked against a file that stayed behind on the machine that made it

bundle.json's key names are the retired script's, deliberately: it is a published machine interface with a live consumer, so the orchestration moved without renaming the artifact underneath it. New facts are added; nothing is renamed.

The reconciliation is VD-D94's equality, both directions, published on every run whether or not it found anything: missing (a declared component with no complete artifact), unasked (a directory no component asked for — the direction nothing checked, and the one that catches a leftover from an earlier, larger set), and instances (more than one is a bundle assembled from two places). Any finding, or any failed component, exits 3 BUNDLE_INCOMPLETE.

Failure behaviour, today: a failed component is recorded with its typed refusal and the run continues; the bundle is marked incomplete. VD-D121 (per-component certification) changes that to stop-at-the-failing-component, and it lands whole rather than half.

The projection tier is derived, never declared twice. A component's tier comes from its own argv (--tier <t>), from the engine default when the verb has a tier and the argv names none, and is absent — a named non-fact — when the verb has no projection tier at all. The one constant (the engine's external default) carries an oracle: a test reds if the shipped --tier help stops saying so.

--explain reaches no engine and writes nothing: it reports every component, its group, its purpose, its verb and its resolved argv, the flags the run would add, and what the set declares it does not export. --explain with --out refuses (BAD_EXPLAIN) — a plan writes nothing.

The run-lock is probed before the first sweep. The set occupies the engine for the sum of its components (the export alone is ~15 min on vehu), so a busy lock refuses now rather than forty minutes in — and rather than as 32 consecutive component failures.
