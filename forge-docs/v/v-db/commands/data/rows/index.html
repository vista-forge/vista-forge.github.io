v db rows
Group Data
Engine access read
Mutates data no
Reversibility not applicable (does not mutate)
Exit classes 2 (usage error)

Synopsis

Section titled “Synopsis”

Arguments

Section titled “Arguments”
Argument Type Required Description
file float yes FileMan file number, e.g. 200 for NEW PERSON.

Flags

Section titled “Flags”
Flag Type Default Env Description
--engine string vehu V_ENGINE VistA engine profile to reach (vehu = YDB, foia = IRIS, local = in-image YDB).
--transport local | docker | remote — — Driver transport: local | docker | remote. Overrides the profile's transport; unset = the profile's own.
--lock-wait duration 30s — How long to wait for the engine run-lock before refusing (0 = skip immediately when busy).
--timeout DURATION duration — — Host wall-clock bound on ONE engine visit; a hung page is aborted engine-side, not just abandoned. Unset = the verb's derived default (180s; a whole-instance sweep verb pins a slower one); negative = no bound (still reapable by hand).
--fields string — — Projection: ';'-separated field numbers, or '*' (engine default: all top-level).
--tier external | internal | raw — — Projection tier (engine default external).
--where list (no splitting) — — Row filter ' ' (repeatable = AND). Ops: = '= > < >= <= contains starts bound 'bound. Stored fields only, evaluated on the INTERNAL value (a pointer takes an IEN); rejected candidates stay charged to examined and show in filtered.
--parent string — — Scope a SUB-file read to one multiple instance: the parent-record IENS, child-first with its trailing comma ('999996,' one level up; 'd1,d0,' two). For a nested-root file (#1.1) the one piece is the branch file number. Without it, a direct sub-file of a top-level parent pages the whole depth walk (rows keyed by emission ordinal, each carrying its full iens).
--with-multiples bool — — Read each record WITH its sub-records: every non-word-processing multiple is projected inline under its field number, recursively, each sub-record carrying its own iens. Without it a '*' read is flat and declares which multiples it left out. A record whose subtree exceeds the bytes budget becomes a typed TREESIZE row naming the record, the multiple and the paged alternative — never a silent trim.
--iens list (separator ,) — — Read exactly these records, in the order given, instead of walking the file: a comma-separated list (repeat the flag to add more). Rows come back in SUPPLIED order, a repeated IEN is served per request (visible as emitted over distinct), and every IEN with no record is named in 'misses' rather than dropped. One paged conversation instead of one round trip per record: measured 253 ms/record through a get loop against ~25 ms/record paged.
--iens-file string — — Read the record list from a file instead of --iens: one IEN per line (a comma-separated run on a line works too), blank lines skipped. '-' reads standard input, which is how a pointer list from another read feeds straight in.
--ids bool — — Attach a reference map to every row: for each pointer (foreign key) field, the file and record it names, plus a 'ref' that 'get --ref' reads back. A variable pointer resolves PER RECORD from its stored global root; a root the dictionary does not declare is resolved by asking which file owns it (marked resolvedBy:root), and named unresolved — never guessed — when no file claims it. Free on --tier internal (the values are already record numbers); on the default external tier it costs ONE extra internal projection of the reference fields per page.
--explain bool — — Report what this read WOULD do and exit, without reading a data page: its population, which predicate each index can position, the cost class, and the command to run instead. Two bounded dictionary reads of this file; never a sweep.
--census FILE string — — --explain only: a census artifact (census.jsonl) to read this file's record count from. The count is never estimated — it comes from a named artifact or it is reported unmeasured.
--indexes FILE string — — --explain only: an index artifact (indexes.jsonl from 'v db indexes --key-sample N --out DIR') to read the KEY measurements from. Without it every index is order-only, because whether a key IS the field's value is the one fact a dictionary read cannot supply.
--profile FILE string — — --explain only: a fields-profile artifact (fields-profile.jsonl) — a predicate on a column measured at zero bound records is a guaranteed-empty walk, said before the walk.
--token string — — Opaque continuation token from the prior page, passed back verbatim.
--out string — — Write EVERY row to this directory as JSONL + a manifest, walking the file to exhaustion instead of returning one page. The manifest carries the merged completeness block, so a truncated artifact says so.
--max-pages int — — Safety bound on the --out walk (0 = unbounded). Hitting it is recorded as a NAMED incompleteness, never a silent stop.
--pace duration — — Politeness gap between the --out walk's engine visits (e.g. 500ms) — host-side spacing for background extracts against a live instance; every page stays bounded regardless.
--max string — — Rows budget (page size; engine default 4000).
--bytes string — — Page payload byte budget (engine default 786432).
--examined string — — Candidates-visited budget for the page (engine default 75000).
--elapsed string — — Engine-time budget for the page in ms (0 is legal: stop after the first candidate; engine default 10000).

Notes

Section titled “Notes”

Hand-written in the owning repository; the facts above are generated.

One bounded page of a file's records over the declared IEN walk. The workhorse read.

--explain reports what the read would do — its population, which index can position which predicate, the cost class and the command to run — without reading a data page. It is documented once, below (The plan — --explain), and works the same on find.

Filtering. --where '<field> <op> <value>', repeatable (repeats AND together). The operator set is a closed table — no client M is ever XECUTEd:

examined 6, filtered 1, emitted 5 — six candidates were visited, one was rejected by the predicate.

Three refusals define the filter surface, and each names its reason:

The first is the closed table refusing to grow. The second is the whole reason the table is closed: DDR XECUTEd client-supplied M as a screen, and a computed field would smuggle site DD M back into the per-candidate loop by another door. The third has one exception, and only one: bound is admissible on a multiple — it reads storage rather than a value, so "this record has sub-records at all" is answerable where "a sub-record equals X" is not (§11.7).

The byte budget. Ask for every field of #200 and one record fills the page:

stopped bytes with examined 2: the second candidate was visited, would not fit, and the page closed cleanly at a record boundary. Cost tracks field count, not row count — which is why a row ceiling alone would not have caught this.

--iens — read the records you name, not the file. Every other population here is a walk. This one is a list you supply, and it exists because the alternative is a loop of single reads: measured, a get per record costs 253 ms (process, lock and envelope, per row) against ~25 ms/record paged — 10× at ten records, and linear in the count.

Three things in that output are the contract:

  • rows come back in SUPPLIED order, not collation order — 2, 1, 2, with each row carrying pos, its place in the list you sent;
  • a repeated IEN is served per request — the list is data, so asking twice answers twice, and emitted 3 · distinct 2 says so out loud;
  • misses is on every page, empty when there are none. A requested IEN with no record is named with the position that asked for it, never dropped:

A hollow record — a subscript with no 0 node — is not a miss. It is a record, and it comes back flagged ("hollow": true). Present-but-empty and absent are different facts, and only one of them is a hole.

--iens-file PATH takes the list from a file — one IEN per line, blank lines skipped — and - reads standard input, which is how a list of pointer values from one read feeds the next:

The list is chunked for you. The dispatch command has a hard engine ceiling (YottaDB's indirection limit), so a cohort of any size cannot ride one request: the host cuts the list into chunks that fit and the cursor is a position in the whole list. A page that runs out of chunk says stopped chunk — the transport ended the page, not the population — and the continuation token picks up inside the same list. A 4,000-IEN cohort walks in three engine visits:

Exit 3, not 0: 1,441 of the records asked for are not there, and an artifact that did not say so would be the whole problem. absent names them; the per-page misses keep their positions.

Resuming needs the same list. The token an --iens read prints carries where in your list it stopped, so pass the same cohort back with it. An edited list refuses rather than serving a plausible subset — the cursor is bound to the list's own identity:

--iens needs engine build VSL*1.0*54 or later, and the host checks before it asks. This one is worth stating plainly: an older engine does not refuse the flag — it never binds the list and reads the whole file instead.

--ids: the reference map

Section titled “--ids: the reference map”

A page of records tells you what each pointer field says. --ids tells you where each one goes, as a parallel map beside the fields — never a changed value, because the value contract is load-bearing everywhere here:

Every ref is a get --ref away (8.8), and a set of them feeds straight into --iens — which is what closes the loop without a join: --ids says where to go, --iens fetches the set in one conversation.

A variable pointer resolves per record. Its type is a bare V and the file it names is data: the stored value is <ien>;<global root>, and the root elects the target from the field's declared set. On the page above, field 2 (DIALOG) is 101.41 on one record and 101 on the next — one field, two files, decided row by row. This is the case FMQL's filter silently matched nothing on.

A root the dictionary does not declare still resolves — and says so:

#100's ITEM ORDERED declares targets 19/60/101.41 and its records store ^ORD(101,, ^RAMIS(71, and ^PS(50.3, — 74 of 799 references over 200 rows on vehu (9.3 %). That is a real, measured disagreement between the dictionary and the data, and FileMan renders those values happily because it dereferences by the stored root and never consults the declared set.

So --ids asks the same question FileMan does: which file owns this root? ^DIC(f,0,"GL") is FileMan's own statement of that, so the answer is read from the dictionary of files rather than guessed — and resolvedBy: "root" marks it, because "the DD declared this target" and "the data pointed here and the DD did not say so" are different provenances and a consumer reconciling against the dictionary needs to know which one it holds. A declared target carries no marker.

When no file claims the root, the entry keeps its old shape — the record number, the root it saw, and why it stopped:

⚠️ This needs VSL*1.0*63 on the engine. Against an older build the flag does not fail — it answers the smaller, older way, naming such a reference instead of addressing it. The refusal sentence tells you which you have: the and no file on this instance claims it either clause is present only when the engine was actually asked.

What it costs. The map needs each pointer's internal value. On --tier internal the page already carries it, so --ids is free. On the default external tier it is one companion read per page — the same request re-issued at the internal tier projecting only the reference fields — which is density-dependent and bounded by roughly doubling the read on pointer-dense rows (measured at demo sparsity, the two tiers time the same: 470 ms vs 444 ms over 20 star rows of #2, because most pointer fields are empty and never resolve). A projection with no reference field in it does no extra read at all. Machine consumers should be on --tier internal --ids, where the question costs nothing.

Every page states its own coverage in an ids block:

The root lookups line appears only when the page needed one. It is one call per distinct root, not per row: measured on 40 rows of #100 field 7, 39 references resolved by root and it cost 3 lookups.

--ids does not combine with --tier raw (IDS_RAW_TIER): that tier returns data nodes, which have no field types to resolve references from. Under --with-multiples the map covers the record's own fields and says so — a sub-record's pointers belong to the sub-file's dictionary, which this map is not built from.

A direct sub-file of a top-level parent depth-walks. #200.02 (the DIVISION multiple under #200 NEW PERSON) pages across every parent's sub-records at once; each row carries its full iens, and population reads sub:<file>:

iens is child-first with its trailing comma ("500,1," = sub-record 500 under parent 1) — reading a row's own IEN off iens rather than off ien alone is what lets you tell three sub-records with the same sub-IEN, under three different parents, apart.

--parent scopes the read to one parent instance — the parent's own IENS, child-first with its trailing comma ('1,' for a direct sub-file one level up; 'd1,d0,' two levels). Scoped, each row's iens is implied and only the sub-record's own ien is printed, and population records the scope:

--with-multiples — the record WITH its sub-records. A plain * is flat and declares what it left out; --with-multiples projects every non-word-processing multiple inline under its field number, recursively, each sub-record carrying its own iens:

Under the flag projection.excluded is empty — there is nothing to exclude — and the note says so. A #63 LAB DATA record comes back with its 63.04 chemistry panels, each carrying its own sub-sub-records: one invocation, decoded, no client-side reassembly.

The crossover — cohorts inline, bulk per sub-file. The inline tree is for a cohort: records you can name, read whole. For bulk extraction of a deep file, prefer the per-sub-file streams (rows 63.04 --out, rows 63.041 --out) and join them downstream by iens — a single lab patient's subtree can exceed any byte budget, and a bulk run that names hundreds of over-budget records is honest but the wrong tool. The two forms compose: same iens vocabulary, same manifest shape.

When a record's tree does not fit. The page closes at a record boundary, so one oversize record never truncates another. That record rides the stream as a typed stub instead:

U-VSL-ROW-TREESIZE names the record, the offending multiple and the paged alternative. It is deliberately not U-VSL-ROW-TOOBIG, which means one oversize value — conflating them hid which limit fired.

Every data --out manifest pairs with its dictionary. Internal-tier data is the portable tier, and it is meaningless without the DD that decodes it: sets decode in the dictionary, dates by their DD type, pointers by their target. So the manifest carries the dictionary's fingerprint as read in the same run —

— and a consumer can verify the pair rather than trust that the two files travelled together. A file whose DD could not be read leaves the pairing unmeasured and says so in incomplete; it never poses as verified.

Nesting depth is no longer a limit. An earlier build served the unscoped walk only for direct multiples of a top-level file, and refused anything deeper. Since the depth-walk engine build (2026-08-13) it rides a generalized odometer over the whole parent chain, so a sub-file at any depth walks file-wide — verified on both engines. #63.041 nests under #63.04, itself a sub-file of #63 LAB DATA — three levels down, and it needs no scope at all:

The IENS is the address that makes it navigable: 1,7059189.8872,2, reads child-first, so this is sub-record 1 of sub-record 7059189.8872 of record 2. --parent is still there when you want one parent's children rather than the file's — that is a scoping choice now, not a workaround. U-VSL-ROW-SUBFILE survives for the case that remains genuinely unanswerable: a parent chain that does not resolve (over 20 levels, or a cycle in the dictionary).

(v db schema 200.02 still works — the dictionary side has no such restriction, and distribution reports sub-file depth.)

The budget demonstration. This is the single most important behaviour to understand, because it is where DDR's central defect was:

Zero rows — but not a silent empty result. The block says exactly what happened: 500 candidates visited, all 500 rejected by the filter, the --examined budget ended the page, and there is more data behind it. Under DDR the identical request returns an empty list with no error and no indication that a scan is under way.

--explain: the plan

Section titled “--explain: the plan”

What would this read actually do, and is there a cheaper way? --explain on rows or find parses the request, reports what it would do, and exits — without reading a single data page.

It is a flag, not a verb. A standalone explain rows … would re-declare every read flag as a copy that can drift; this way there is one grammar.

What it will not tell you

Section titled “What it will not tell you”
it reports it refuses to report
the population, in the engine's own words (file, index:B, sub:44.001, ien-list(12)) a selectivity estimate — that needs statistics this tool does not keep
a cost class: seek · seek+filter · walk · walk+filter a row estimate, ever
which index can position which clause, and under what licence a seek it cannot license (see below)
the record count — only from a --census artifact, cited with its instance and moment a count from anywhere else. Without the artifact it says unmeasured and names the command that makes one
a guaranteed-empty verdict, from a --profile artifact an emptiness it has not measured
the command to run, with its basis that the command is equivalent — that is the equivalence check's job

The licensing rule

Section titled “The licensing rule”

A prefix seek is proposed over a sampled-identity key, bounded by the longest key the sample measured. Equality and range seeks are never proposed from a sample — they are listed as possible, sample-supported, residual under-return risk, because a seek over a truncating index positions past the stored bucket and the kept predicate never runs on what the seek never visits. contains and negations position nothing. A compound index positions on its leading key only. A conditional index is order-only: it holds a subset of the file. And <field> bound is answered by walking the whole index — that is a claim about membership, not keys, so truncation cannot touch it, but it needs a registration that declares no SET CONDITION.

Three artifacts, verified first

Section titled “Three artifacts, verified first”

Each is passed with --indexes / --census / --profile, and each is checked before a number from it appears: the manifest must be beside it, its verb must match, the stream must match the sha256 the manifest claims, and it must come from this instance — an artifact from another site is a typed refusal (ARTIFACT_INSTANCE). An engine that never declared an identity cannot be matched against, and the plan says so rather than assuming.

Without --indexes, nothing is licensed. Whether a key is the field's value costs a record read per sampled entry per cross-reference — a data read, which a plan does not make. So the planner reports order only and names the command that would change the answer.

The equivalence check

Section titled “The equivalence check”

The plan's proposal replaces a filtered walk with a positioned seek, and the two are equivalent only if the index positions exactly and holds every record. The second is unprovable for a traditional definition. Check it on your own data:

Measured 2026-08-14 on both gold engines, this agreed on every non-empty pair tried (#44 B 23=23, #19 B 348=348 vehu / 337=337 foia, #200 B 125=125 vehu / 3=3 foia, #3.1 B 5=5). It is also a standing probe — P16-equivalence in the capability sweep — so a truncating or conditional index becomes a red gate rather than a review finding.

Measured properties

Section titled “Measured properties”

Synopsis, arguments and flags: generated from the contract (dist/v-contract.json, command rows) and rendered on the documentation site.

One bounded page of records walked in IEN order from the data root — the population is the walk, never a stored list, so nothing is missed because an index was stale. Five population shapes, all carrying the same completeness discipline:

  • The file walk (default): row-id order, resumable by token.
  • A sub-file (rows 4.03…): file-wide at any depth — every parent's instances, each row carrying its full iens; --parent '28,' scopes to one multiple instance (population sub:19.01@28,).
  • A supplied IEN set (--iens '.5,1,999' / --iens-file -): rows return in supplied order with a pos per row; a repeated IEN is served per request (visible as emitted over distinct); every IEN with no record is named in misses, never dropped. One paged conversation instead of a get loop — measured ~10× cheaper (253 ms → ~25 ms per record). This is how a pointer list from another read feeds straight back in.
  • The tree read (--with-multiples): every non-word-processing multiple projected inline under its field number, recursively, each sub-record with its own iens. A record whose subtree exceeds the bytes budget becomes a typed TREESIZE row naming the record, the multiple and the paged alternative — never a silent trim. Without the flag, a * read is flat and declares which multiples it left out.
  • The whole-file artifact (--out DIR): walks to exhaustion, JSONL + manifest with the merged completeness block; --max-pages is a named incompleteness, --pace spaces the walk's engine visits. Both dials refuse without --out (BAD_OUT_DIAL).

--where filters on stored fields at the internal value (§6.4); rejected candidates stay charged to examined and appear in filtered. --ids attaches the reference map (§5.8). --explain reports what the read would do — population, which predicate each index can position (citing supplied artifacts, verified first), cost class, and the exact command to run — for two dictionary reads and zero data pages. Executed: example (all six faces).
