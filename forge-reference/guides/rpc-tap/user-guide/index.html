v rpc-tap — User Guide

Note

Hand-written, not generated — the words are v-rpc-tap’s, from docs/guides/user-guide.md. What this site guarantees about them is coverage, not correctness.

This guide takes a developer, installer, or operator from an empty checkout to a tap that is installed on a live VistA, capturing RPC traffic, draining it, and uninstalled byte-clean — using only the supported toolchain. Read the README first for the one-paragraph “what and why”; this document is the how.

Golden rule — the driver stack is the only way in. Every touch of a live M engine (install, arm, drain, ad-hoc inspection) goes through the m-driver stack: v pkg …, v rpc-tap …, or m engine exec …. Never docker exec … mumps / iris session into an engine — that is an org red-gate, not a shortcut.

1. Concepts in five minutes

Section titled “1. Concepts in five minutes”

The tap has three moving parts, split across an in-engine M package and a Go host:

part routine / package runs where job
in-path capture VSLRTAP (spliced into CALLP^XWBPRS) inside every broker handler, on the live RPC path copy the RPC name (mode 1) or name + params + result (mode 2) into a per-job ring; emit zero I/O; self-disable on any fault
off-path reaper VSLRTRP (a #19 OPTION under TaskMan) one background job, ~every 10 s enforce the lease/duration/overflow disable conditions, reap dead-$J rings, keep the tap safe
host seam VSLRTH + the Go host (v rpc-tap) the driver job (off the RPC path) arm/disarm/status, drain records out, committrim the durable prefix after they’re safe downstream

Storage is a per-broker-job ring at ^XTMP("VSLRT","buf",$J,seq) — the ^XTMP global, which lives in a non-journaled TEMP region on a conventional VistA, so the tap adds zero journal load. Each job’s ring is bounded (drop-oldest past a depth cap; the reaper disarms capture entirely if the aggregate blows an absolute cap and nothing is draining). Records leave via drain (which deletes nothing) and are only deleted from the engine by committrim after they are safely stored downstream — an at-least-once contract (a crash between drain and ack re-drains, and duplicates are de-duped by (inc, $J, seq)).

Capture modes: 1 = names-only (RPC name + metadata), 2 = full-payload (adds request params and the result — this is PHI; treat mode-2 output as clinical data).

Safety posture: the in-path body runs under its own fail-open $ETRAP — the first error kills the ON flag system-wide and resumes the broker byte-identically, so a bug in capture can never corrupt an RPC or crash a session. This is proven under deliberate fault by the M test suites and re-verified live during the vetting campaign (see the production-vetting report).

2. Prerequisites

Section titled “2. Prerequisites”

Toolchain (host side)

Section titled “Toolchain (host side)”
  • m — the cross-engine M toolchain (m test / m lint / m engine exec / m sync).
  • v — the v CLI busybox, which mounts both v pkg (the KIDS install/uninstall path — the only supported install mechanism; never a bespoke installer) and this repo’s v rpc-tap domain.
  • Go 1.24+ (airgapped config per the org go-dev guide) to build the host + KIDS builder.
  • direnv — the repo .envrc does source_up, inheriting the shared engine/VistA credentials from ~/data/vista-forge/auth.env (never committed). After direnv allow, VISTA_ACCESS / VISTA_VERIFY (and the M_* engine vars) are simply present.

Engines

Section titled “Engines”
  • A live VistA reachable through the driver stack. The reference gold masters are vehu (YottaDB, broker 127.0.0.1:9430) and foia-t12 (IRIS CE). Docker-transport paths need no credentials (programmer context in-container); the RPC-broker path (signon, the load rig) needs VISTA_ACCESS/VISTA_VERIFY.
  • For the M unit tests only: the bare test engines m-test-engine (YDB) / m-test-iris (IRIS) — no VistA, no install.

The MSL/VSL relationship

Section titled “The MSL/VSL relationship”

The three VSLRT* routines are the VistA-specific (v-layer) part of this tool. They reference no STD*/VSL* library routine and do zero crypto/JSON/I/O — a hard dependency-purity gate (make m-purity) keeps the in-path body minimal and safe. Only the tests pull in STDASSERT from m-stdlib (the MSL). So: you build/lint/test the M package with the m toolchain against m-stdlib, and you install it with v pkg — the same KIDS path every VistA package in the org uses. There is no separate installer.

3. Build & verify (no engine mutation)

Section titled “3. Build & verify (no engine mutation)”

From the repo root:

make check must be green before you install anything. It runs the M unit suites on both bare engines and the Go tests — no live VistA required.

4. Build the site-specific KIDS package

Section titled “4. Build the site-specific KIDS package”

The splice overwrites the national XWBPRS routine, so the shipped routine is regenerated from the target site’s current XWBPRS — never a frozen repo copy. This keeps the tap’s two bare hook calls (D req^VSLRTAP() / D rsp^VSLRTAP()) layered onto whatever patch level the site actually runs.

Under the hood make kids stages src/VSLRT*.m, runs v rpc-tap splice to produce the spliced routine, and calls v pkg build to assemble the transport .KID. Nothing here touches a live engine. The point of regenerating per-site: the two bare hook calls are layered onto the site’s XWBPRS at its patch level, so back-out restores exactly what was there.

splice — lay the hook calls onto a site’s XWBPRS

Section titled “splice — lay the hook calls onto a site’s XWBPRS”
Flag Default What it does
--in PATH — The site’s current XWBPRS.m, read and never modified
--out PATH stdout Where to write the spliced routine. Left unset it prints, so you can diff before it becomes a build input

The diff is the acceptance test a site can run for itself: a correct splice adds the two D req^VSLRTAP() / D rsp^VSLRTAP() calls and changes nothing else. If the input is not a real XWBPRS, the splice refuses (SPLICE) and names what it could not find to hook rather than emitting a routine that would install cleanly and capture nothing.

5. Install on a live engine (v pkg)

Section titled “5. Install on a live engine (v pkg)”

Installation, verification, and back-out are exclusively v pkg operations against a drift-gated KIDS build.

A clean install reports the three VSLRT* routines as NEW and XWBPRS as CHANGED, and files the VSLRT REAPER #19 OPTION. --auto-snapshot writes the pre-image sidecar (dist/kids/vslrtap.preimage.kids) that back-out consumes.

The install is classed side-effecting (it overwrites a national routine), so v pkg requires an explicit pre-image (--auto-snapshot/--snapshot) to remain reversible. Do not use --allow-overwrite (that discards the pre-image and makes byte-clean back-out impossible).

6. Operate the capture lifecycle

Section titled “6. Operate the capture lifecycle”

All control verbs reach the engine through the driver seam. Set the target once via env (VRPCTAP_ENGINE / VRPCTAP_TRANSPORT / VRPCTAP_CONTAINER) or pass the flags each time.

The per-invocation form is --engine / --transport / --container, and --container is the one that names the machine: it sets M_<ENGINE>_CONTAINER for the driver, so --engine ydb --container vehu and --engine ydb --container m-test-engine are the same engine and two different instances. A control verb run against the wrong instance succeeds — it is a real engine — so name it deliberately rather than inheriting whatever the environment last exported.

arm — turn capture on

Section titled “arm — turn capture on”
  • --mode — 1 names-only, 2 full-payload.
  • --ttl — host lease in seconds; the reaper disarms if the host stops renewing it (dead-man switch — a crashed host cannot leave capture running forever).
  • --dur — absolute arm cap in seconds (0 = indefinite); enforced in-path too, so it fires even if the reaper is dead.

⚠️ Mode 2 captures PHI. Request params and results include patient data. Only arm mode 2 where that is authorized, and treat every drained record + downstream object as clinical data (the production egress target is FedRAMP-High US GovCloud — see §8).

status — what is armed, and how much is buffered

Section titled “status — what is armed, and how much is buffered”

drain — read the records out (deletes nothing)

Section titled “drain — read the records out (deletes nothing)”

drain pulls the live records, correlates them into sessions (grouped by (inc, $J), ordered by seq, classified complete / unpaired / names-only), and sets a per-job watermark so the in-path trim will not drop undrained records. It deletes nothing — durability is the drainer’s job via the next step.

committrim — reclaim, only after downstream ack

Section titled “committrim — reclaim, only after downstream ack”

Deletes the durable prefix [head..seq] for one job and advances head. Call this only after the drained records are safely stored downstream (S3-acked). This is the at-least-once seam: a failure between drain and this call re-drains the same records (de-duped later by (inc, $J, seq)), so nothing is lost. The engine enforces it: a --seq beyond the job’s drained watermark refuses with TRIM_BEYOND_WATERMARK (the hint names the watermark to trim at), and a job that has never been drained refuses with TRIM_NOT_DRAINED — a trim can never destroy an undrained record.

disarm — turn capture off

Section titled “disarm — turn capture off”

Drive traffic at the broker

Section titled “Drive traffic at the broker”

drive and load are the two client-side verbs. Neither touches the engine through the driver seam: they open real Broker sockets, so they take --addr (the broker’s host:port, vehu’s is 127.0.0.1:9430) instead of the engine flags. They exist so a tap run has something to capture without a Delphi CPRS client in the loop, and load is what the vet-p*.sh scripts drive.

drive — fire an exact sequence, once

Section titled “drive — fire an exact sequence, once”

The instrument for “what does this one RPC do”:

Flag Default What it does
--rpc NAME — RPC to fire; repeatable, and fired in the order given
--param VALUE — One literal parameter passed to each fired RPC (the shape XUS AV CODE takes); empty fires them no-arg
--signon off Authenticate the session first (XUS SIGNON SETUP → XUS AV CODE) using VISTA_ACCESS/VISTA_VERIFY
--context NAME — After signon, create this broker application context (XWB CREATE CONTEXT, a #19 OPTION) so its RPCs become callable — an authenticated RPC is unreachable without one

load — fire a mix under concurrency

Section titled “load — fire a mix under concurrency”

The measurement instrument:

Flag Default What it does
--workload NAME names-clean Named preset: names-clean (a clean L7 latency workload) or mixed
--rpc NAME — An explicit mix, repeatable. Overrides --workload when set
--oracle TSV — Replay the recorded post-signon CPRS sequence from a P1 workload-oracle TSV. Overrides both --workload and --rpc — this is what makes a load run a fidelity replay rather than a synthetic mix
--signon off Authenticate each session, as a real client fleet would
--concurrency N 50 Concurrent broker sessions
--total N 500 Total RPCs across all sessions
--duration D 0 Run for a wall-clock duration (e.g. 30s) instead of --total, which it overrides

The workload sources form a precedence chain — --oracle beats --rpc beats --workload — so a run that sets more than one is not ambiguous, but it is also not doing what a reader of the command line might assume. Set one.

The --stagger default exists for a reason the troubleshooting table records: the broker’s xinetd cps rate-limit rejects a thundering herd of connects, so the rig spaces them.

The measured results these produce, and the limits on reading them, are in the production-vetting report; the re-runnable scripts are in reproduce the load tests.

7. Uninstall — byte-clean, every time

Section titled “7. Uninstall — byte-clean, every time”

A clean back-out reports verifyClean:clean (routines match the re-applied artifact) and foreignRestore:exact (the national XWBPRS is byte-for-byte the pre-install routine). Then clear the ring and confirm the engine is pristine:

The scripts/vet-p2.sh / vet-p3.sh scripts perform exactly this teardown automatically (and via a shell trap, so even a failed run leaves the gold master clean) — see the reproduce-load-tests guide.

If a raise of Kernel MAX SIGNON ALLOWED was done for a load run, it must be restored (the reference baseline on vehu is 30). The vet scripts do this too.

8. Drain → downstream (egress)

Section titled “8. Drain → downstream (egress)”

drain emits records to the host; the Go pipeline (internal/pipeline) ships them to an object store and calls committrim only after the store acks (at-least-once). The production sink is S3 in the FedRAMP-High US GovCloud partition — egress of RPC traffic (including PHI) is authorized only there, and Config.Validate pins the partition/region. The MemSink/FileSink adapters carry the flow today; the real AWS S3 sink and a CLI ship verb are not yet built (see the roadmap in the README).

9. Safety properties (why this is installable on a national routine)

Section titled “9. Safety properties (why this is installable on a national routine)”
  • Zero in-path I/O. $IO is the live client socket at both hook points; the capture body never issues a WRITE/READ/OPEN/USE. Proven by the L-block suites.
  • Fail-open. The first error in capture self-disables the tap system-wide and resumes the broker byte-identically (the RPC completes as if the tap were absent).
  • No shared written node in-path. Each broker job writes only its own ring with an atomic $INCREMENT counter — no cross-session contention, which is what lets the tax stay flat as sessions scale.
  • Bounded storage. Per-job depth cap (drop-oldest, watermark-respecting) plus a reaper aggregate-overflow disarm; a stuck host trips the disarm rather than losing data.
  • Non-interference proven with a real client. A genuine Delphi CPRS session ran through the armed tap with correct capture and zero interference (vetting P1).
  • Reversible. Byte-clean v pkg uninstall --restore --verify on both engines.

Measured cost: +48 µs/message names-only, +226 µs/message mean full-payload (both < 1 ms) at the stable load gate — see the production-vetting report.

Typed refusals

Section titled “Typed refusals”

Every refusal carries a stable code, so a script can branch on the reason rather than on the message text. Every code this domain can raise:

Code Exit Raised by Means What to do
USAGE 2 any verb The invocation did not parse — an unknown flag, a missing required argument, a value outside an enum Run it with --help; the message names the offending token
NO_DRIVER 4 the control verbs No engine driver could be reached Check the driver binary and the --engine/--transport/--container you named. drive, load and splice need no driver at all
TRIM_NOT_DRAINED 4 committrim A trim on a job that has never been drained Drain first — a trim can never destroy an undrained record
TRIM_BEYOND_WATERMARK 4 committrim --seq past the job’s drained watermark The hint names the watermark to trim at
BROKER 1 drive A broker socket failed — connect, read, or write against --addr Check the address and that the listener is published; v rpc-debug doctor walks the whole path
SIGNON 1 drive --signon could not authenticate VISTA_ACCESS/VISTA_VERIFY in the environment (direnv source_ups them), and the account not locked out
CONTEXT 1 drive --context could not be created The named #19 OPTION must exist on the instance and be a type-B broker context listing the RPCs you intend to call
READ 2 splice --in could not be read — classed as a usage error, because the path came from the command line Check the path; the routine is read, never modified
WRITE 1 splice --out could not be written Check the directory exists and is writable
SPLICE 1 splice The splice could not be produced from the supplied XWBPRS The input must be the site’s real routine; the message names what it could not find to hook

The two committrim refusals are exit 4, not 3 — they are refusals to act, not findings about something examined. READ and WRITE sit in different classes for the same reason: an unreadable --in is a bad argument, an unwritable --out is a runtime failure part-way through work already done.

10. Troubleshooting

Section titled “10. Troubleshooting”
symptom cause / fix
v pkg install says “already installed” but routines look wrong a corrupt half-install; re-run with --commit --heal (purges a #9.7 entry with no usable 0-node) then install.
an RPC fired through drive/signon takes ~1 s and looks like a timeout a param-hungry RPC fired param-less hits the broker’s ~1 s M-error path — not a tap fault. Use a clean-dispatch RPC (e.g. XWB GET BROKER INFO) for smoke tests.
m engine exec on IRIS returns empty stdout set M_IRIS_BIN (the m-iris driver isn’t auto-discovered) and M_IRIS_NAMESPACE=USER; without the namespace the exec silently succeeds with no output.
capture “stops” on its own under heavy load with nothing draining working as designed: the reaper’s aggregate-overflow disarm fired (a stuck-host backstop). Drain + committrim promptly, or raise OVCAP.
ring never shrinks though you’re draining drain deletes nothing by design — you must committrim (after downstream ack) to reclaim.
load rig fails 100 % at higher concurrency the broker’s xinetd cps rate-limit (a thundering herd of connects); the load rig staggers connects (--stagger 25ms) to stay under it.
