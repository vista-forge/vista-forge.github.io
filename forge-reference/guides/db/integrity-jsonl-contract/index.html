The instance-integrity artifact — what a consumer gets

Note

Hand-written, not generated — the words are v-db’s, from docs/guides/integrity-jsonl-contract.md. What this site guarantees about them is coverage, not correctness.

v db integrity --engine <e> --out <dir> writes two files: integrity.jsonl (one JSON object per line, one line per audit row) and manifest.json (what the run was, WHICH instance it measured, and whether it finished). It is the committed-artifact form the baseline/delta comparison (VD-D110, step 4) reads row-for-row, and the sibling of the catalog and index-sweep contracts: one manifest, one complete flag to branch on.

What this artifact is: a CENSUS of one VistA instance’s self-consistency at one moment — every accepted integrity-finding class (VD-D105), per file, as counts with denominators and content folds. It is never a verdict (VD-D106): a stock release build is measurably nonzero in every class, no absolute count sets a failing exit, and red is the delta comparison’s word, not this artifact’s.

The oracle contract binds the rows. For the record/dictionary sweeps and the 3x-b expansion planes (keys, descent, pairs, the entries-only index arm), the rows reproduce the frozen harness-tier oracle’s per-(class, file) rows exactly — class names, value spellings, emission conditions — and the three-instrument harness (docs/design/instance-integrity-harness/instance-integrity-host-via.py) verifies exactly that against instance-integrity-probe.py on both engines, with a planted divergence per sweep required to red.

1. integrity.jsonl — one line per audit row

Section titled “1. integrity.jsonl — one line per audit row”
field always? meaning
class yes the ruled class vocabulary (below). denom:* rows are denominators, not findings
file yes the file number as a STRING (.44 ≠ 0.44) — an identity, never a quantity. -- on instance-wide denominators
sub index plane and denied:policy only the index plane’s row identity is per (file, SUBTREE) — one file checks many indexes; on denied:policy it names the sweep that met the denial
value yes the canonical byte-exact spelling — k=v pairs, every count/fold/IEN a verbatim string. Row identity for the delta is (class, file, sub, value) (VD-D110’s (class, file, count, content-fold), with sub carrying the index plane’s extra key)

Identity is bytes. Counts, folds, IENs and header claims are copied through from the engine as string literals — never parsed into numbers and re-rendered (measured defect class: JSON number normalization respelled the decimal IEN .999 as 0.999 on foia #.44). A consumer that parses value must not round-trip it through floats before comparing.

2. The class vocabulary

Section titled “2. The class vocabulary”

Oracle-shared classes (the frozen oracle’s grammar — an absent row is not a zero: totals accumulate engine-side before each row’s emission condition, so a file can feed denominators and emit no row):

class one row per value emitted when
header-ledger file with a GL root claim=,walk=,last=,max= (claim/last are the 0-node’s RAW pieces; "" is a real state distinct from 0; max is the walked max IEN in M-canonic spelling) always
hollow file n=,withchild=,fold= hollow records > 0
hollow-sub file n=,withchild=,walked=,fold= hollow depth-1 sub-records > 0
ptr-dangling · ptr-malformed-freetext · ptr-noncanonical-resolving · vptr-dangling · vptr-malformed file n=,fold= count > 0 (the A5/D109 malformed split)
set-not-in-table · set-case-drift · date-nonconforming · num-noncanonical file n=,fold= count > 0 (grammar only — input transforms never execute, VD-D108)
key-register keyed file keys= always — the census count (VD-D105); the CHECK is the key family below (VD-D111)
key-checked measurable key — file is <keyed file#>/<key name> (the number the KEY register itself spells, so a sub-file key’s row carries the SUB-FILE number) top-level: recs=,ixkind=,maxtuple=; sub-file: recs=,parents=,scope=,parent=,ixkind=,maxtuple= (scope is the uniqueness index’s declared ROOT TYPE — W whole sub-file, I per parent — READ, never inferred) always per checked key
key-duplicate checked key n=,tuples=,fold= — records beyond the first sharing a DECLARED-shape tuple (SEQUENCE order, each position truncated to its uniqueness-index subscript’s declared MAXIMUM LENGTH, length-prefixed); null-tuple records EXCLUDED from the population count > 0
key-null-field checked key n=,fold= — FileMan’s second key promise: a key field must hold a value count > 0
key-tuple-overlong checked key n= — tuples past the 400-byte guard, counted by name, never subscripted count > 0
key-not-walked keyed sub-file whose parent declares no multiple field parent=,reason=no-multiple-field — a named non-fact, never a zero-count check row always when it applies
sub-census (top-level file, sub-file) with any walked sub-record — file is <top-level file#>/<sub-file#> (VD-D112’s ruled identity) depth=,recs=,pv=,vv=,sv=,dv=,nv= — the sub-file plane’s denominators always per walked pair
ptr-dangling-sub · ptr-malformed-freetext-sub · ptr-noncanonical-resolving-sub · vptr-dangling-sub · vptr-malformed-sub · set-not-in-table-sub · set-case-drift-sub · date-nonconforming-sub · num-noncanonical-sub (file, sub-file) n=,fold= — the top-level predicates restated one level down, same fold recipes (VD-D112) count > 0
hollow-sub-deep (file, sub-file) n=,withchild=,fold= — hollow sub-records at walk level ≥ 2 ONLY; depth-1 stays hollow-sub, and the two never double-count depth ≥ 2 and count > 0
ptr-pair-dangling (source file, target root) pair carrying dangling mass — file is <source file#>/<target root>, the root byte-exact as the dictionary (plain) or the stored value (vptr) spells it; a root may itself contain : or / — split the identity on the FIRST / only n= — counts only, no threshold, no cap (VD-D114); membership churn rides the source file’s own dangling folds, which cover the identical membership count > 0
index-entries-checked entries-only fed row that stored entries=,stored=1 — the entry direction’s denominator (the oracle’s g-sweep spelling) always when stored
index-entries-dangling entries-only fed row n=,fold= — the oracle’s emission condition: only when nonzero; on a checked row the ABSENCE of this row is a measured zero (the index-entries-checked row is the denominator that makes that reading safe) count > 0
index-entries-stored-empty entries-only fed row that stored nothing stored=0 — a named non-fact: no leg ran always when it applies
excluded:audit-class pinned audit-class file subtrees=,records= always — the A4/D108 exclusion, contract-verified on-engine every run
meta:descent-max — the DECLARED descent bound (6), echoed from the engine; sub-records at the bound with deeper declarations are denom:descent-beyond-max, never silently dropped always
denom:* — the sweep denominators (denom:files-with-gl, denom:ptr-values, denom:dd:*, denom:key-register, denom:keys-registered, denom:keys:<disposition>, denom:descent-files, denom:descent-beyond-max, …) always

Explicit index-plane classes, BOTH-direction rows (the host’s own grammar, VD-D107 — here zeros are EXPLICIT: a measured 0 renders as n=0, never as an absent row, because this grammar has no frozen-oracle emission condition to honor; the entries-only classes above DO have one, the g sweep’s, and follow it instead — the zeros-vs-absence rule is per class, stated here):

class one row per value
index-population fed (file, subtree), both directions rule=terminal2,directions=<both|entries>,trunc=<list> — the feed is part of the ledger, so a register drift is a row delta; the trailing list is EMPTY on an entries row (the leg truncations parameterize does not run on it, and the engine refuses a nonempty one)
index-checked both-direction fed row that stored entries=,records=,stored=1 — the per-row denominators
index-dangling · index-missing both-direction fed row that stored n=,fold= — zeros included
index-longvalue-untested both-direction fed row that stored n= — .01 values past the 180-byte probe guard, counted apart
index-stored-empty both-direction fed row that stored nothing stored=0 — a named non-fact: the register said stored, the engine visit found nothing, neither direction ran
index-records-not-run entries-only fed row that stored reason=entries-only — the NAMED non-fact for the record→entry leg that did not run (VD-D113): never a zero, never an absent row a consumer could read as “measured none”. A stored-empty entries row emits no not-run row — stored=0 already says nothing ran
index-unmeasurable reason (sub carries it) n= — the register cannot fully interpret these stored subtrees (kind-mumps, kind-record-level, …)
index-inexpressible reason (sub carries it) n= — register-interpretable but outside the engine’s terminal2 vocabulary (ien-shape)
denom:index-registered · denom:index-stored · denom:index-rows-fed · denom:index-rows-fed:both · denom:index-rows-fed:entries — the plane’s denominators; fed(both) + fed(entries) + Σ unmeasurable + Σ inexpressible (+ audit-class) = stored
denied:policy (file, sweep) reason= — a policy-denied file is LOUD; the audit did not read it

The population feed rules (VD-D107 unchanged — storage-driven inference appears nowhere — with the direction split VD-D113 ruled): the entry→record preconditions gate ADMISSION — kind regular+documented, walkable, measured ienPositions, arity 2 with an unfalsified terminal IEN (terminal2), entries under this file’s own root. The record→entry preconditions choose which LEGS run — the .01 among the key fields (the engine’s record→entry direction probes the record’s .01), no declared SET CONDITION, no declared TRANSFORM FOR STORAGE: all three hold → directions=both; any fails → directions=entries, the entry direction alone. The engine wire is the five-field row <file>|<b64 subtree>|terminal2|<truncations>|<directions> — directions REQUIRED with no default (a 4-field row is a typed engine refusal), truncations REQUIRED EMPTY on an entries row. Truncations (both-direction rows only) are declaration-first: a registered MAXIMUM LENGTH probes 0,<len>; a registration with neither transform nor length probes full length only; a traditional definition registers nothing and rides the pinned FileMan stock family 0,30,63 (a documented-contract pin, the A4/D108 pattern — stated per row, never assumed silently).

3. manifest.json

Section titled “3. manifest.json”

The shared v-db manifest (see the catalog contract §3): instance (station/domain/FileMan — WHICH engine these rows measure), request, records, sha256/bytes, incomplete/complete. Two rows of run provenance ride details, because the step-4 comparison needs them (VD-D106/D110):

  • details.generatedAgainst — the VSL+MSL builds this host was generated from. A run that completed did so under the armed E1 source pin, so this is a verified fact about the ENGINE’s installed sources, not a hope.
  • details.sweeps / details.classes / details.coverage — the per-sweep cost lines, the class census (ruled classes with explicit zeros), and the D107 coverage statement with its named buckets.
  • writtenAt — measurement data (when the audit ran; the same-day discipline the oracle contract requires), not a self-stamp: this artifact is a snapshot-in-time, never a regenerate-and-diff-gated derivation.

--to <file#> (a dev/smoke run) lands as a NAMED incompleteness and the check exit; a baseline must never be captured from an incomplete artifact.

4. What a delta consumer must know

Section titled “4. What a delta consumer must know”

The shipped consumers are v db integrity-compare (the delta and the shipped-state ledger, with the pinned outcome vocabulary clean · delta · attention · stopped) and v db integrity-report (the VD-D109 attribution view) — user guide §8.21/§8.22; the committed baselines and the derived ledger live in baselines/integrity/, gated by scripts/integrity-baseline-check.py. The rules they read by:

  • Row identity is (class, file, sub); the compared content is value. Aggregate counts are never compared (VD-D106: identity is per finding row).
  • On the oracle-shared classes — the record/dictionary sweeps AND the 3x-b planes (key family, *-sub, pairs, index-entries-*) — a row appearing/disappearing IS the delta signal (emission conditions are contract); on the both-direction explicit index plane, zeros are present, so only the POPULATION rows appear/disappear — and a population change means the register moved, which is itself a reportable fact, not noise.
  • Engines move under sanctioned operations — a VSL install measurably moves the header ledger (#19 joined the divergence set after one install cycle), so re-baselining after installs is a named cadence obligation (VD-D106), and comparisons must be same-instance, stated-build.
  • Exact-duplicate rows are folded once (several sweeps re-emit the same audit-class x-row); rows sharing a key with DIFFERENT values would mean the engine moved mid-run — both are kept, and the comparison will surface them.
