VistA Forge

Hardened. Industry-standardized. AI-Integrated.
The VA VistA system, re-imagined.

VistA is the US Department of Veterans Affairs' health record — the software running 1,200 hospitals and clinics for more than forty years. It works, and it is not going to be replaced. What it has never had is the everyday machinery other industries take for granted: automated testing, changes that prove they install and prove they can be taken back out, and a way in for developers who have not spent years learning it. VistA Forge builds that machinery around VistA — without changing the system the VA already trusts.

The whole of it, in three words

Hardened. Industry-standardized. AI-Integrated.

Each word is a claim, and each claim is the answer to a question a hospital system has to be able to answer about its own software: can you prove a change is safe? · can anyone but a specialist work on it? · can it move at the speed the work now demands?

Hardened Can you prove a change is safe? Every change passes the same gates, and anything installed can be removed again — proven, not promised. Industry-standardized Can anyone but a specialist work on it? The work moved to ordinary, mainstream technology. VistA keeps running underneath, untouched. AI-Integrated Can it move at today's speed? An AI agent works the same surface a person does, and clears the same gates before anything ships.

Claim one

Hardened — any change must be proven before it reaches anyone

A forty-year-old system nobody dares touch is not safe — it is stuck. That is where critical systems usually end up: no one can show a change is safe, so the safe answer becomes no, and the system slowly falls behind the care it is supposed to support. Proving every change is what makes the opposite possible. Because each one is fully tested and can be taken straight back out, the system can change often and quickly — safe, tested, rapid, reversible.

What it is

A pre-flight checklist for software — and, like a pre-flight checklist, it exists so the thing can fly often, not so it stays on the ground. A fixed routine every change goes through, in the same order, whoever made it and however small it is.

How it works

The checks are built into the tools people work with rather than written down in a policy. That is the whole difference: a rule in a document depends on someone following it under pressure; a rule inside the tool does not. There is no override, and no meeting where an exception gets granted.

What it is worth

  • The system can evolve — safely, quickly, and reversibly. That is what all of it is for. The proof is not overhead; it is what makes frequent change possible at all.
  • Improvements can land in weeks rather than waiting years for a moment when everyone feels brave enough.
  • A change that fails a check never reaches a live system — the failure happens on a developer's machine, not in front of a clinician.
  • Anything that does go wrong comes out completely, and you can show that it did rather than hoping so.

Claim two

Industry-standardized — the hard part stopped being a prerequisite

The people who can change VistA safely learned how over many years, and there are fewer of them every year. That is the real risk in a forty-year-old system — not that the software fails, but that the understanding of it retires. That understanding is now written down as working, tested code. Using it no longer requires having spent years learning it.

What it is

Everything the old hands knew, written down as working code with tests behind it, under names that say what they do. The knowledge is still there — it is just no longer something you have to have lived through to use.

How it works

Each hard-won piece of know-how became one named, documented, tested thing that anyone can use. The person using it does not need to know what it touches inside VistA, or what the VA happens to call it. The expertise did not go away; it stopped being a prerequisite.

What it is worth

  • The expertise stops retiring. Written down and tested, it outlives the people who worked it out.
  • You hire from the ordinary job market instead of competing for the few people who already know VistA.
  • Someone new is useful in days rather than after years of apprenticeship.
  • Nothing is rewritten or replaced, so there is no migration to survive and no day when everything changes at once.

Claim three

AI-Integrated — an AI does the work, and it is checked the same way a person’s is

The question is not whether AI can write software — it can. It is whether you can accept work you did not watch being done. In a hospital system, normally you cannot. Here you can, because an AI goes through exactly the same steps a person does and has to pass exactly the same checks. Its work arrives with the same evidence attached, which is what makes it usable at all.

What it is

A system built so that an AI is simply another user of it — not bolted on afterwards, and not given a private entrance of its own.

How it works

What the AI reads about the system is produced from the system itself, so it cannot quietly go out of date. And because the checks live inside the tools rather than in a policy, they apply to the AI without anyone having to arrange it.

What it is worth

  • Work that was never worth starting becomes practical. The backlog of small improvements that could never justify a project of their own.
  • The work arrives with the same evidence a person's does, so it can be accepted on the same terms rather than on trust.
  • Nothing about the safety of the system changes because of who — or what — did the work.

How it actually works, measured and named.

The mechanism behind the three claims: why the rigour is what makes it fast, the numbers the gates enforce, the tools a developer uses, the shape of the stack, why it is built on registries, every repository in the organisation, and the design rules the whole thing agrees on.

The bridge

Speed and safety are not a trade-off here — they are the same mechanism.

What slows a critical system down is not the work. It is uncertainty. Every change needs a human to judge whether it is risky, and that judgement is slow, scarce and fallible — so changes are batched up, shipped rarely, and each release is bigger and riskier than the last, which justifies shipping even more rarely. That is the loop a forty-year-old system ends up in, and it is why it stops evolving.

Every technology below kills one specific source of uncertainty and replaces it with evidence a machine produces on demand. Once uncertainty is cheap, frequent change becomes affordable — and small frequent changes are far safer than big rare ones. Aviation got safer and more frequent at the same time, through checklists, instrumentation, simulators and mandatory procedure. Nobody thinks a pre-flight checklist slows aviation down.

What’s here, by developer task

The everyday loop M never had.

Write M like any modern language

m fmt (a formatter that rewrites the syntax tree, never the text), m lint (query-driven rule engine, with XINDEX/Kernel compatibility profiles), and m lsp (an LSP 3.x language server) all sit on one parser — m-parse, which embeds the tree-sitter-m grammar as WebAssembly and runs it through wazero. Static Go binaries, no C bindings, no C toolchain at runtime.

Test against a real engine, with coverage

m test runs *TST.m suites on a live YottaDB or IRIS engine via ^STDASSERT, with machine-readable results; m coverage produces standard LCOV coverage reports with per-module coverage gates. Every library in the org is built test-first and gated on both engines.

Stop hand-rolling utilities — three standard libraries

m-stdlib is a pure-M library of 38 STD* modules: data formats (STDJSON, STDXML, STDCSV, STDREGEX), encoding, testing (STDASSERT, STDMOCK), crypto and auth (STDCRYPTO, STDJWT), networking (STDHTTP, STDS3), plus dates, logging, collections, strings, math, and filesystem. Above the waterline, v-stdlib adds 24 VSL* modules — 62 modules across the two libraries.

Reach an engine exactly one way

m-driver-sdk defines the vendor-neutral driver contract — typed verbs, a structured engine-error model, honest capability documents, and an executable conformance gate any driver binary must pass. Everything above the seam reaches an engine only through this contract.

Treat VistA patches as code

v-pkg gives KIDS — VistA's native package/patch format — a real lifecycle: parse, classify, lint, decompose, assemble, roundtrip, diff, build, install, verify, snapshot, restore, uninstall, attest. Decompose a distribution into a git-diffable component tree and reassemble it byte-identically; install, verify, and cleanly back out against a live engine.

Administer VistA with plain-noun commands

The sysadmin platform pairs each engine-side VSL* module with a host-side v <domain> command, generated — not hand-wired — from the VSL manifest. Plain nouns a developer can guess: v pkg, v rpc-debug, v rpc-tap. VA product names never appear in a command; a lint gate enforces the plain language.

Run VistA on your own machine

vista-iris publishes a multi-arch container of WorldVistA on IRIS for Health Community — the full site build is baked into the image, so it boots already operational: Management Portal and REST, the RPC Broker that serves CPRS (the VA's Computerized Patient Record System), HL7 messaging over its Minimal Lower Layer Protocol, and the IRIS superserver. Fictitious test data only.

Drive it all with an AI agent

Every binary shares one command grammar (clikit): --output text|json|auto, a versioned JSON envelope, a deterministic exit-code ladder, and a reflected schema command — so an agent invokes the same gated surface a human uses and gets machine-parseable results.

The stack at a glance

Classic VistA stays put. An industry-standard layer goes on top.

The important line in this stack is not a technical one — it is the line between the knowledge you need and the knowledge you don't. Below it sits classic VistA: Kernel, FileMan, KIDS, the RPC Broker — four decades of software that works, and that has always demanded deep, arcane, institutional knowledge to touch safely. Above it sits an industry-standard layer that covers those internals in ordinary, mainstream technology. Developers and AI agents work at the top layer. The institutional knowledge stays below the line, in code that is tested rather than remembered.

Why a library layer changes who can work on VistA. Every one of those boundaries used to be crossed by knowing things: which global to reach into, which Kernel entry point to call, which side effect to expect. Each is now a documented call with a test behind it. The M Standard Library (MSL) makes M a peer of other mainstream languages instead of a special case; and the VistA Standard Library (VSL) reframes Kernel, KIDS and the remote-procedure-call (RPC) Broker in modern mainstream terms, with a command surface in plain nouns. The learning curve drops from years of institutional apprenticeship to reading an API — which is exactly what lets an AI agent be productive here, and a new human developer too.
Architecture

Why registries — VistA’s failure mode, inverted.

Classic VistA integrates by reaching into other packages' globals: every application owns its own data and freely reads and writes everyone else's, with the agreements recorded in prose nobody executes, naming policed by human review, and patches installed with no reliable back-out. The result is the coupling archaeology every VistA developer knows. Here the same concerns are declared, generated, and red-gated — one discipline, source-tag → generate → registry → red-gate, at every layer.

Design principles

What the whole stack agrees on.
  • Git-canonical source. M code lives in .m files under version control; the database is the runtime, not the repository.
  • Dual-engine parity. YottaDB and IRIS are both first-class; the same suites gate both, and engine specifics live only inside the drivers.
  • One seam. Every tool reaches a live engine through the m-driver-sdk contract — no hand-rolled transports, verified by an executable conformance gate.
  • Gated, not aspirational. Layer boundaries, seam contracts, registries, build specs, and doc links are generated, drift-gated artifacts checked on every push — not conventions enforced by review.
  • Declared data ownership. A module states which VistA files it touches and how; a source scan red-gates undeclared access, and exactly one module may write a given file.
  • Reversible by proof. Engine mutations are audited into a hash-chained attestation ledger, installs capture pre-images, and a release tag can only be cut when a full install → uninstall cycle diffs byte-clean.
  • Static, dependency-free binaries. CGO_ENABLED=0 everywhere; even the M parser runs as WebAssembly.
  • One contract, many surfaces. A single command grammar and reflected schema mean CLI flags, JSON envelopes, and agent tools never drift.
  • Test-first. Every module is built test-first with per-module coverage gates; conformance suites run against the test vectors published with the standards themselves.
  • Plain nouns. A command wraps an insider VistA subsystem in a name a developer can guess — and a lint gate keeps it that way.
